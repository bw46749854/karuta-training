### 1.2 作るときの確認

- データは、タグ `sample` の `kimariji-data.js` から、スクリプトで写した（手で打ち直していない）。
- 写した結果を実行して、サンプルのデータと突き合わせた。歌番号・静的決まり字・並び順まで、100首すべて一致した。

### 1.3 テストを先に書いて、失敗を確かめた

データを空にし、歌番号の型は中身を書かずに、テストを動かした。13 件のうち 6 件が失敗した。

| 失敗したテスト | 理由 |
|---|---|
| 歌番号は 1〜100 がちょうど1回ずつ現れる | 歌が0首 |
| 静的決まり字の分布が §4.2 のテストベクタと一致する | 同上 |
| 1字決まりは「むすめふさほせ」の7首 | 同上 |
| 決まり字グループは46グループ | グループが0個 |
| 歌番号の型の2件（1〜100 は歌番号になる、0 と 101 は歌番号にならない） | 中身を書いていない |

通った 7 件のうち 5 件（文字、一意性、最短性、グループの定義、グループの名前の重複）は、データが空だと何も調べずに通ってしまう。残りの 2 件（範囲の外の整数と、整数でない数は歌番号にならない）は、中身のない関数が常に失敗を返すので通った。

そこで、データを入れた後に、データを1か所ずつわざと壊して、テストが失敗することを確かめた。

### 1.4 わざと壊したデータと、失敗したテスト

| 壊し方 | 失敗したテスト |
|---|---|
| 歌番号の重複（100番を99番に） | 歌番号、グループの定義 |
| §3 にない文字（む → ム） | 文字、1字決まり |
| 一意性の崩れ（うか → う） | 一意性、分布、1字決まり |
| 空の静的決まり字（せ → 空） | 一意性、分布、1字決まり |
| 最短性の崩れ（あい → あいう） | 最短性、分布 |
| グループの歌が足りない（「あさ」から 64番を消す） | グループの定義 |
| グループの歌が重複（「あさ」に 31番を2回） | グループの定義 |
| グループの名前が最短でない（あさぼ → あさぼら） | グループの定義 |
| グループが足りない（「あわ」を消す） | グループの定義、46グループ |
| グループの名前の重複（あわ → あり） | グループの定義、名前の重複 |
| 2首の歌番号の入れ替え（74番と 65番） | **なし** |

**テストで見つけられないこと**：2首の歌番号を入れ替えても、§8.3 のテストはどれも失敗しない。§8.3 は、データどうしの食い違いを見るテストで、歌番号と決まり字の対応が正しいかは見ないため。この対応の正しさは、§1.2 のサンプルとの突き合わせだけで確かめている。

### 1.5 テストの作り方

- 一意性・最短性・グループの定義は、100首のすべての組み合わせ（9,900 組）を調べる。100首は有限なので、fast-check で無作為に選ぶより、全部調べるほうが強く、毎回同じ結果になる。
- fast-check は、歌番号の型に使った。範囲の外の整数と、整数でない数（NaN・無限大を含む）は、数に限りがないので無作為に選んで調べる。1〜100 は全部調べる。
- 文字は、仕様 01 §3 のとおりコードポイント1つを1文字として数える。

残りの 146 個は、データの1行を丸ごと空にする変異（`[87, "む"]` → `[]`）。歌番号の型の作り方が失敗を投げ、データを読み込めなくなるので、Stryker は「見つけた」ではなく「エラー」に数え、スコアから除く。見逃しではない。

## 2. テストがないときに通す設定を外した

- 日付：2026-10-31
- Vitest の `passWithNoTests` と Stryker の `allowEmpty` を外した（[段階 1 の記録](stage-1-checks.md) §4）。

外した後の動きを確かめた。

| 設定 | 外した後に止まること | 確かめ方 |
|---|---|---|
| Vitest の `passWithNoTests` | テストのファイルが1つも見つからないと失敗する（`include` の書き間違いなど） | 合わないファイル名を指定して実行し、終了コード 1 |
| Stryker の `allowEmpty` | 変異の対象に関わるテストが1つも動かないと失敗する | テストのない `application` だけを変異の対象にして実行し、終了コード 1。`allowEmpty` を付けると 0 |

段階 1 の記録では「外さないと、テストのないパッケージが合格してしまう」と書いていたが、正確ではなかった。テストの設定はワークスペース全体で1つなので、ほかのパッケージにテストがあれば、テストのないパッケージがあっても失敗しない。テストのないコードを止めるのは、`domain` と `application` ではカバレッジの閾値（段階 1 の記録 §1 の #18）。

### 3.2 形の決め方

- 候補集合は、既読の歌を渡して作る `CandidateSet.afterReading()` でしか作れない型にした。練習に選んだ歌だけを候補にする書き方（サンプルの札流しの挙動、§9）は、型の上でできない。
- 決まり字の計算の引数は、歌と候補集合だけ。場に取り札があるか、空札かは、引数にない。§5.1 の「決まり字に影響しない」を、形で満たす。
- 候補にない歌の決まり字を求めると、失敗を投げる。§4.1 は候補に含まれる歌についてだけ定義しているので、候補にない歌を渡すのはバグとして扱う。
- LCP は、§3 のとおりコードポイント1つを1文字として数える。

### 3.3 テストを先に書いて、失敗を確かめた

候補集合と決まり字の計算を、中身を書かずにテストを動かした。新しい 41 件がすべて失敗した（中身がないことによる失敗）。それまでの 13 件は合格のまま。中身を書いた後は、54 件すべて合格した。

### 3.4 性質テストの入力

- 候補集合は、既読の歌を無作為に選んで作る。試合の序盤・中盤・終盤のどれも試すよう、既読が少ない場合・半分くらいの場合・多い場合を混ぜた。3,000 回の生成で数えた既読の数の分布は、0〜9 首が 14%、10〜39 首が 16%、40〜60 首が 43%、61〜90 首が 17%、91〜99 首が 11%。
- P4（候補が1首だけ）と、100首すべてが候補の場合は、数に限りがあるので全部調べる（それぞれ 100 通り）。

### 4.2 テストを先に書いて、失敗を確かめた

4つのモジュールを、中身を書かずに（失敗を投げるだけにして）テストを動かした。新しい 197 件がすべて失敗した。それまでの 54 件は合格のまま。中身を書いた後は、251 件すべて合格した。

### 4.3 テストの作り方

- ローマ字の表は、仕様の表をそのまま JSON に写し、80 のつづりをすべて確かめる。決まり字に現れない行（だ行、ぱ行など）も含む。
- 「表のつづりに分けられるときだけ変換でき、つづりのかなをつないだものになる」ことを、英小文字3文字までのすべての並び（18,278 通り）で確かめる。比べる相手は、表のつづりで先頭から切っていく書き方で、実装（母音の後ろで区切る）とは別の書き方にした。4文字以上は fast-check で無作為に選ぶ。
- R1（決まり字はどのつづりでも入力できる）は、静的決まり字とその先頭部分（158 通り）の、すべてのつづり（196 通り）を調べる。
- そのほかの性質（R2〜R4、S1、M1〜M4）は、fast-check で無作為に選ぶ。M3 は、問の札の決まり字をどの順で答えても正解になることも、別のテストで確かめる（正解になる場合を必ず試すため）。

### 4.4 チェックの結果

| チェック | 結果 |
|---|---|
| 単体テスト | 251 件合格 |
| カバレッジ | 行・分岐・関数・文ともに 100% |
| ミューテーション | スコア 100%。新しい4つのモジュールの変異のうち、168 個を見つけ、見逃しは 0 個。4 個は除外（下記）、17 個はエラー（下記） |

- **除外した変異**：答えと決まり字を比べる行（`answer.kind === "kana" && answer.kana === kana`）。種類の確認を常に真にする変異は、同等な変異（結果が変わらない）。かなに直せない答えには `kana` がないので、種類を確かめなくても比較は失敗するため。この行の条件の変異（4 個）を、理由を書いたコメントで除外した。
  - コメントを付ける前に、付けずに実行して確かめた。見逃したのはこの1個だけで（スコア 99.76%）、同じ行のほかの3個は見つけていた。
- **エラーの 17 個**：ローマ字の表の行を空にする変異など。モジュールの読み込みで失敗するので、Stryker は「見つけた」ではなく「エラー」に数える。見逃しではない（§1.6 と同じ）。
- **書き直したところ**：最初の版では、ローマ字の区切り方の正規表現に、同等な変異が2個残った。末尾に母音のない残りは、どう切っても変換できないため。「母音で終わらないローマ字は変換できない」と先に確かめる形に書き直し、どちらも見つけるようになった。
