# クラウドセッションの指示書（2026-11-05）

ユーザーが席を外している間に、クラウドセッションが開発を進めるための指示。

- この文書は `CLAUDE.md` の一部の規則を、今回だけ読み替える（§3）。ここに書いていないことは、`CLAUDE.md` と `docs/` に従う。
- 長いセッションでは会話が要約される。迷ったら、この文書を読み直す。
- ユーザーへの質問で止まらない。ユーザーはいない前提で進める。判断できないものは保留して、次へ進む（§5）。

## 1. 時間

- **16:00 JST（07:00 UTC）に畳み始め、16:30 JST（07:30 UTC）までに §8 の報告を push する。** 時刻は `date -u` で確かめる。
- 利用の上限に当たると、途中で止まることがある。止まっても失わないよう、1つの意図ごとにコミットして `dev` に push する。
- 時間が足りないときは、範囲を削る。品質は下げない（§2）。

## 2. ゴール

計画（[全体計画](../plan.md) §3）の順番どおりに進める。

| 区分 | 内容 |
|---|---|
| 必達 | 1. §7 の準備<br>2. 段階 3 の残り：`ui` の共通の枠（文言の表、トップに戻るボタン）と、`adapters-web` のポート実装（契約テストつき）<br>3. 段階 4 の 1：設定画面（全項目）と、入口として最小限のトップ画面（仕様 04）<br>4. 段階 4 の 2：札流し（仕様 05） |
| できれば | 5. 段階 4 の 3：札流し（複数枚）（仕様 06）<br>6. さらに時間が余れば、計画の順に次の画面へ |
| やらない | `main` の変更、段階の完了の宣言、公開、札面の本番の素材、サンプルの修正、正常系も含めたサンプルの動作のテスト |

- 各画面は、[開発の進め方](../workflow.md) の手順どおりに作る（仕様 → 受け入れテスト → テストを先に書く実装）。
- 各画面の終わりに、[設計方針](../design/principles.md) §6 の完了の定義を確かめる。再現手順書の該当する不具合は、回帰テストにする。
- **画面を途中で終えない。** 残り 45 分を切ったら、新しい画面の実装を始めない。残りの時間で仕様書だけ書くのはよい。

## 3. 今回だけの読み替え

| `CLAUDE.md` の規則 | 今回の扱い |
|---|---|
| 仕様は承認を取ってから作る | 仕様書の状態を「承認待ち（実装済み）」にして、そのまま実装へ進む。「承認」とは書かない |
| 選択肢があるときはユーザーが決める | §4 の範囲は自分で決める。決めたことと理由を §8 の報告に書く |
| push は確認を取ってから | `origin` の `dev` への push は確認しなくてよい。ほかの push は §5 のとおり行わない |
| 段階の完了はユーザーが確認する | そのまま。文書には「完了候補」と書き、全体計画の状態を「完了」にしない |

## 4. 自分で決めてよいこと

手戻りが小さいもの。決めたら仕様か報告に書く。

- 新しい仕様書（04 以降）の中身。根拠は、取扱説明書の【確認済み】【変更】、【不具合】の本来の動き、決定事項に限る。
- ADR が「各画面の仕様で決める」としたもの：個々の文言、画面の配置の細部、押せない操作を隠すか残すか、保存せずに離れるときに確かめるか、など。
- 設定画面を定義から自動で作るかどうか（ADR-0003 論点 D）。
- 設定の初期値の仮置き。値は段階 5 で調整する。札の配置の初期値だけは決まっている（仕様 03 §6.1）。
- 開発用の依存の追加（Testing Library、jsdom など）。
- 画面の切り替えの作り。新しい実行時依存を足さない形にする。
- **仮の札面**。`CardFaceProvider` のポートと、文字だけの仮のアダプタを作る。
  - 札には歌番号を出す。答えになるので、決まり字は出さない。
  - サンプルの画像は持ち込まない。出所を確かめておらず、公開リポジトリの履歴に残るため。
  - 下の句の文字データは足さない。マスターデータの仕様にないため。
  - 本番の札面は段階 5 で、アダプタの交換で入れる。
- size-limit の 100 kB は仮の値（[段階 1 の記録](stage-1-checks.md) §2）。超えたら機能を削らず、値を上げて、実測と理由を記録に書く。起動時間の予算 500 ms は緩めない。

## 5. 決めずに保留すること

次に当たったら、やらずに §8 の「判断待ち」に書き、影響しない作業へ進む。

- 承認済みの文書（ADR、設計方針、仕様 01〜03、全体計画）の変更が要るとき。新しい ADR が要るなら「提案中」の状態で書くだけにして、それに依存しない作り方で進める。
- 新しい実行時依存の追加。
- 根拠のない新しい機能。思いついたものは §8 の「提案」に書く。
- `main` への push とマージ、プルリクエストの作成、タグ、GitHub の設定の変更、公開。クラウドの環境はどのブランチへの push も止めない。`main` の保護に頼らず、自分で守る。
- remote `karutaTraining` への push。サンプルの報告フォームへの送信。

## 6. ローカルのメモにしかなかった規則

クラウドには届かないので、ここに書く。

- **報告は日本語で書く。** コミットメッセージは英語のまま。
- **設計の判断は、担当の上級エンジニアとして行う。** 論点、軸（設計方針 §1 の優先順位）、トレードオフ、選ぶものと理由を書く。規則の文言に従う前に、その規則の目的を確かめる。
- **設定値は根幹。** ADR-0003 の形に従い、局所的な直しで済ませない。
- **入力を甘くしない。** サンプルの入力の便利さ（空白の無視など）を持ち込まない。答えの入力は仕様 02 が正。
- **動作は、人に見えるもので確かめる。** スクリーンショットや計算後のスタイルで見る。DOM のクラスや内部の状態で判断しない。
- **決まり字の計算の基準は静的決まり字。** 歌の全文は持たない（仕様 01）。
- **テスト用の部品**は `src/test-support` に置き、カバレッジと Stryker の対象から外す。
- **版の固定**：TypeScript は 6.0.3（typescript-eslint が 6.1 未満のみ対応）。pnpm の `minimumReleaseAge` に新しすぎる版を拒まれたら、`minimumReleaseAgeExclude` を足さず、少し古い版を選ぶ。CI の action は SHA で固定する。

## 7. 準備（クラウドの環境）

2026-11-05 に公式の文書で確かめた内容。実際の環境と違ったら、環境に合わせて、§8 に書く。

- **ブランチ**：`dev` で作業する。`claude/` のブランチは作らない。別のブランチを環境から強制されたら、そこで作業を続け、§8 に書く。
- **コミットの名前**：クローンには名前の設定がない。次を設定する。

  ```bash
  git config user.name bw46749854
  git config user.email 165236241+bw46749854@users.noreply.github.com
  ```

- **Node**：リポジトリは 24 以上が必要で、環境には 20〜22 しかない。`nodejs.org` から 24 系を入れ、`PATH` の先頭に置く。
- **pnpm**：`packageManager` のとおり 12.16.1 を使う（`corepack enable pnpm` か `npm i -g pnpm@12.16.1`）。その後 `pnpm install --frozen-lockfile`。
- **E2E のブラウザ**：Playwright の配布元は、既定の許可リストにない見込み。`playwright install` が失敗したら、入っている `/usr/bin/google-chrome`（`CHROME_PATH`）で `chromium` のプロジェクトだけを動かす。設定を変えるなら、`CHROME_PATH` があるときだけ効く形にする。Firefox・WebKit・iPad は CI に任せる。
- **CI**：`.github/workflows/ci.yml` は登録されているが、実行の履歴がまだ 0 件。2026-11-05 13:45 JST の `dev` への push でも動かず、check suite も作られなかった。GitHub に障害はなく、原因は分かっていない。
  - 最初の push の後に `gh api repos/bw46749854/karuta-training/actions/runs` で一度だけ確かめる。動いて失敗したら直す。
  - 動かなければ、原因を調べずに進める。リポジトリの設定を見ないと分からない可能性が高く、時間を使う価値がない。
  - その場合、Firefox・WebKit・iPad は確かめられない。§8 の「確かめていないこと」に書く。ユーザーが手元の `pnpm verify` で確かめる。
- **GitHub の操作**：`gh pr` などの GraphQL は使えない。`gh api` を使う。タグは push できない。
- **時間のかかるコマンド**：手前で待てるのは既定で 2 分。`pnpm verify` はバックグラウンドで動かす（手元の実測は、今の規模で 2 分 45 秒。画面が増えると E2E の分だけ延びる）。
- **コミット前のチェック**：フックが動かない環境もあるので、`pnpm check:fast` と `pnpm test` を自分で動かす。`pnpm verify` は画面を終えるたびに動かす。

## 8. 報告

`docs/records/stage-4-review.md` に書く。**画面を1つ終えるたびに更新して push する**（途中で止まっても残るように）。

1. できたものと、試し方（コマンドと、見るとよい操作）
2. ユーザーの承認が要る文書の一覧
3. 自分で決めたこと（論点、選んだもの、理由、変えるときの手間）
4. 判断待ち（§5）
5. 提案（仕様に入れていないもの）
6. 確かめていないこと（CI の結果、実機、Chromium 以外のブラウザなど）

あわせて、[全体計画](../plan.md) の状態、[文書の一覧](../README.md)、段階の記録を更新する。
