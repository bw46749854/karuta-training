# 設計方針と、それを守らせる仕組み

この文書は、作り直しにおける設計の原則と、その原則を「人の注意力」ではなく「機械的なチェック」で守らせる方法を定める。
人が書いたコードも AI が書いたコードも、同じゲートを通る。

方針の変更は ADR（`docs/adr/`）を書いてから行う。

## 1. 品質特性の優先順位

判断が衝突したときは、上にあるものを優先する。

1. **ルールの正しさ** — 決まり字変化・判定・配分などの競技ルールが仕様どおりであること
2. **変更容易性** — 仕様変更や機能追加が、影響範囲の小さい変更で済むこと
3. **テスト容易性** — すべての振る舞いが、決定的（毎回同じ結果）に自動テストできること
4. **移植性** — 公開先（Web・iOS・Android・PC・Steam）を増やしても、ルールと画面のコードが変わらないこと
5. **性能** — 起動時間とバンドルサイズの予算を守ること（[ADR-0001](../adr/0001-technology-stack.md)）

## 2. アーキテクチャ

### 2.1 層と依存の向き

依存は必ず内側（ドメイン）に向かう。内側の層は外側の層を知らない。

```
        apps/*（合成ルート：部品の組み立て）
          │
   ┌──────┼─────────────┐
   ▼      ▼             ▼
  ui   adapters-*    （各公開先の起動処理）
   │      │
   ▼      ▼
  application（ユースケース・進行・ポート定義）
          │
          ▼
       domain（競技ルール）
```

| パッケージ | 責務 | 依存してよいもの | 禁止 |
|---|---|---|---|
| `packages/domain` | 競技ルール。歌・決まり字・候補集合・判定・配分。純粋関数と不変な値だけ | なし（標準ライブラリのみ） | DOM、時刻、乱数、I/O、例外による制御、外部ライブラリ |
| `packages/application` | ユースケースと、練習セッションの進行（状態遷移）。ポート（インターフェース）を定義する | `domain` | DOM、React、具体的な保存先・タイマー・通信 |
| `packages/adapters-web` など | ポートの実装（保存・時計・乱数・通信・札面の描画素材など）。公開先ごとに用意する | `application`、`domain` | `ui` |
| `packages/ui` | React コンポーネント。状態を表示し、操作をコマンドとして渡すだけ | `application`（公開 API）、`domain`（**型のみ**） | `adapters-*`、ルールの計算 |
| `apps/web` など | 合成ルート。どのアダプタを使うかをここで1回だけ決める | すべて | ビジネスロジック |

この境界により、次のような差し替えが **アダプタ1つの変更** で済む。

- 札面の素材（仮の画像 → 文字とフォントで組む札面）
- 保存先（localStorage → Capacitor / Tauri のストレージ → Steam Cloud）
- 入力デバイス（タッチ・キーボード → ゲームパッド）
- 公開先（Web → iOS / Android / PC / Steam）

### 2.2 ポート（外界との接点）

ポートは `application` が定義し、アダプタが実装する。1つのポートは1つの関心事だけを持つ（インターフェース分離）。

| ポート | 役割 |
|---|---|
| `Clock` | 現在時刻（単調増加）の取得 |
| `Scheduler` | 指定時間後の通知（タイマー） |
| `Random` | 乱数（0 以上 n 未満の整数）。テストでは決めた値を返す偽の乱数を与えられること。形と作り方は [ADR-0002](../adr/0002-randomness.md) |
| `SettingsRepository` / `BoardRepository` など | 設定・盤面などの保存と読込（保存単位ごとに分ける） |
| `CardFaceProvider` | 札面の描き方の提供 |
| `ReportGateway` | 報告の送信 |
| `Logger` | ログ出力 |

公開先固有の機能（実績、振動など）も、必要になった時点で個別のポートとして追加する。

### 2.3 「関数型の核、命令型の殻」

- 練習セッションの進行は、`(状態, イベント) → (新しい状態, 副作用の指示)` という純粋な遷移関数で表す。
- 「800ms 後に次へ」「保存する」などの副作用は **データとして返す** だけにする。実行するのは外側（アダプタ側の実行器）。
- 時刻と乱数は必ずポート経由で受け取る。このため、テストでは偽の時計と、決めた値を返す偽の乱数を使い、タイミングが絡む流れも決定的に再現できる。

### 2.4 入力の抽象化

タップ・クリック・キーボード・ゲームパッドは、入力アダプタで「カーソル移動」「決定」「取消」「かなを1文字入力」「札を選ぶ」などの **意味のあるコマンド** に変換してから扱う。
画面とルールは入力デバイスを知らない。すべての操作は、コントローラーだけでも実行できるように設計する。

## 3. 原則の具体化

### 3.1 SOLID

| 原則 | このプロジェクトでの具体的な形 |
|---|---|
| 単一責任 | モジュールは「変更理由」で分ける。例：決まり字の計算、ローマ字→かな変換、回答の判定、出題順の生成は別モジュール |
| 開放閉鎖 | 練習モードは共通の契約（インターフェース）を実装する独立したモジュールとして追加する。新しいモードの追加で既存モードを変更しない |
| リスコフの置換 | 同じポートの実装はすべて、同じ **契約テスト** に合格しなければならない（例：`CardFaceProvider` のすべての実装が全100首と空札の札面を返せる） |
| インターフェース分離 | ポートは小さく保つ。何でも入った `Platform` のような巨大インターフェースは作らない |
| 依存性逆転 | ポートは使う側（`application`）が定義し、実装（アダプタ）は合成ルートで注入する |

### 3.2 ドメインモデリング

- **不正な状態を表現できない型にする。** 例：歌番号は 1〜100 しか取れない型（ブランド型）にする。セッションの状態は判別可能なユニオン型（`kind` で分岐する型）にする。
- **値は不変。** 更新は新しい値を返す。
- **真実の情報源は1つ。** 遊び方によって変わるもの（決まり字変化・候補集合）は保存せず、その場で計算する。変わらない事実は、確かめ済みの固定のデータとして持ってよい。ただし、互いに導出できる関係にあるデータどうしは、食い違いがないことをテストで確かめる。例：静的決まり字と決まり字グループは固定のデータとして持ち、食い違いをテストで見つける。決まり字変化は、静的決まり字を基準にその場で計算する（[競技ルール仕様](../spec/01-karuta-rules.md) §4、§7、§8.3）。
- **想定内の失敗は `Result` 型で返す。** 例外はバグ（起こってはならない状態）にだけ使う。
- **用語はユビキタス言語に従う。** 用語と、コード上の名前の対応は仕様書の用語集で定義し、コードもそれに合わせる。

### 3.3 境界での検証

外から入ってくるデータ（保存データ、通信の応答、URL パラメータ）は、境界でスキーマ検証してから内側に渡す。
保存データにはスキーマのバージョンを持たせ、変更時はマイグレーション関数とそのテストを必ず書く。

### 3.4 UI

- コンポーネントは表示とコマンド発行だけを行う。ルールの計算をしない。
- 画面の文言は1か所に集約する（将来の多言語化とテストでの参照のため）。
- アクセシビリティ（ロール・ラベル・フォーカス順）を満たす。E2E テストもロールとラベルで要素を探す。

### 3.5 性能

- 起動の流れ（最初の画面が操作できるまで）には、その画面に要るものだけを入れる。
- 札面は起動の流れに入れない。札面を使う画面で、表示する札の分だけ読み込む。
- 画像などの素材は、コードに埋め込まない（base64 など）。ファイルとして持ち、size-limit の予算に含める。現行サンプルは札の画像 102 枚を base64 で1つのファイル（18.6MB）に埋め込み、練習の画面ごとに丸ごと読み込んでいた。

## 4. テスト戦略

| 種類 | 対象 | 道具 | 合格基準 |
|---|---|---|---|
| ルールのテストベクタ | 競技ルール（決まり字・判定など） | 言語非依存の JSON + Vitest | 全件合格。移植時も同じデータを使う |
| プロパティベーステスト | ルールの性質（例：決まり字は候補が減っても長くならない） | fast-check | 全件合格 |
| 単体テスト | `domain`・`application` | Vitest | 行・分岐カバレッジ 95% 以上 |
| ミューテーションテスト | `domain` | Stryker | ミューテーションスコア 80% 以上（テスト自体の質を測る） |
| 契約テスト | すべてのポート実装 | Vitest | 同じポートの全実装が同じテストに合格 |
| コンポーネントテスト | 操作を持つ UI 部品 | Testing Library | 主要な操作と表示 |
| E2E テスト | ユーザーストーリー単位 | Playwright（Chromium / WebKit / Firefox、iPad 相当の画面サイズとタッチ操作） | 全ストーリー合格 |
| 見た目の回帰 | 主要画面 | Playwright のスクリーンショット比較 | 差分ゼロ、または承認済み |
| アクセシビリティ | 主要画面 | axe | 重大な違反ゼロ |
| 性能 | バンドルサイズと起動時間 | size-limit、Playwright | 予算内 |

テストは仕様から書く。仕様書の各ルールは、対応するテストベクタまたはテストを持つ。

テストは実装より先に書く。受け入れテスト（E2E）を先に書き、その内側の部品を「テスト → 実装 → 整理」の順に作る。手順と例外（スパイク・見た目の試作）は [開発の進め方](../workflow.md) に定める。

## 5. 守らせる仕組み

「気をつける」ではなく、違反したら **CI が失敗する** ようにする。

| 守らせたいこと | 仕組み | タイミング |
|---|---|---|
| 層の依存の向き | パッケージ間の依存宣言（pnpm は宣言していない依存を import できない）＋ TypeScript のプロジェクト参照＋ dependency-cruiser のルール | CI |
| `domain`・`application` で DOM を使わない | 両パッケージの `tsconfig` の `lib` から DOM を外す（使うとコンパイルエラー） | 型チェック |
| `ui` から `domain` へは型のみ参照 | dependency-cruiser で `type-only` 以外の依存を禁止 | CI |
| 循環参照の禁止 | dependency-cruiser の `no-circular` | CI |
| ルール層の非決定性の排除 | ESLint の `no-restricted-globals` / `no-restricted-properties` で `Date`・`Math.random`・`setTimeout`・`performance` などを `domain`・`application` で禁止 | lint |
| 型の抜け道の禁止 | `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`。typescript-eslint の `strict-type-checked` に加え、`no-explicit-any`・`no-non-null-assertion`・型アサーション禁止・`switch-exhaustiveness-check` | 型チェック・lint |
| 単一責任の崩れの早期検知 | ESLint の `complexity`（10）、`max-depth`（3）、`max-params`（3）、`max-lines-per-function`（50）、`max-lines`（300） | lint |
| lint 抑制の乱用防止 | 抑制コメントには理由の記載を必須にする（`eslint-comments/require-description`） | lint |
| 使われていないコード・依存の除去 | knip | CI |
| `console` の直接使用の禁止 | ESLint の `no-console`（`Logger` ポートを使う） | lint |
| カバレッジとテストの質 | Vitest のカバレッジ閾値、Stryker のスコア閾値 | CI |
| 性能予算 | size-limit（バンドルと素材の大きさ）、Playwright（起動時間） | CI |
| 書式の統一 | Prettier | コミット前・CI |
| main ブランチの保護 | プルリクエスト必須、CI 合格必須 | GitHub の設定（リポジトリ所有者が設定する） |
| 設計判断の記録 | アーキテクチャに関わる変更・新しい実行時依存の追加には ADR を必須とし、プルリクエストのテンプレートで確認する | レビュー |
| AI による実装も同じ規則に従う | リポジトリ直下の `CLAUDE.md` にこの方針の要点と参照先を書く | 常時 |

コミット前には速いチェック（書式・lint・変更ファイルの型チェック）だけを走らせ、重いチェックは CI で行う。

## 6. 完了の定義

変更は、次をすべて満たしたときに完了とする。

- 対応する仕様（`docs/spec/`）が更新されている
- 仕様の各ルールに対応するテストがあり、CI がすべて合格している
- 画面の変更では、対応する受け入れテスト（E2E）が合格している
- 再現手順書（`docs/spec/00-sample-repro-steps.md`）のうち関係する不具合は、「直したら確かめること」が回帰テストになっている
- 新しいポート実装は契約テストに合格している
- アーキテクチャに関わる判断は ADR に記録されている
- 抑制コメントには理由が書かれている

## 7. 未決の設計論点

次の論点は、この文書ではまだ決めていない。[全体計画](../plan.md) の段階 3 で、ADR として決める（論点の詳細は [取扱説明書](../spec/00-sample-manual.md) §8.2）。

- **設定値の管理**：設定値をどこで管理するか、依存の向き（設定画面・各画面・保存先の関係）、初期値を1か所で持つこと（DRY）、変更したときの影響範囲。§2.2 には保存と読込のポート（`SettingsRepository`）があるだけで、これらは決めていない。全体設計の根幹にあたる。
- **練習モードの共通の契約**：§3.1 の開放閉鎖の具体的な形。練習の進行（状態遷移）の形と、結果（正解・誤答・スキップ）の記録の持ち方。
- **文言の管理**：§3.4 で「画面の文言は1か所に集約する」としたが、言い回しの基準と、メッセージ・ボタンを全体で統一する方法は決めていない。
- **画面に表示する情報**：何を表示し、何を余計とするかの基準。
- **機器・画面の大きさ**：どれくらいの粒度で分け、どこまで対応するか。アプリ版の起動時間の予算を守る基準の端末。
