# 開発の進め方

1つの機能を、どんな手順で作るかを定める。何をどの順番で作るかは [全体計画](plan.md)、設計の規則は [設計方針](design/principles.md) に書く。

人が書くコードも、AI（Claude）が書くコードも、同じ手順と同じチェックに従う。

## 1. 基本方針

- **仕様が先。** 作るものは、先に仕様書（`docs/spec/`）に書き、承認されてから作る。仕様にないものは作らない。
- **テストが先。** 実装の前に、仕様からテストを書き、失敗することを確かめる。
- **品質は人の注意ではなく、仕組みで保証する。** 設計方針 §5 のチェックに合格しない変更は入れない。

## 2. 1つの機能の作り方

外側（受け入れテスト）と内側（単体テスト）の、2重の流れで作る。

```
仕様を書く → 承認
  ↓
受け入れテストを書く → 失敗を確かめる ─────────────┐
  ↓                                                  │
  内側の流れ（必要な部品ごとに繰り返す）             │
    テストを1つ書く → 失敗を確かめる                 │
    → 通る最小の実装 → 整理（テストは通ったまま）    │
  ↓                                                  │
受け入れテストが通る ←────────────────────────────┘
  ↓
完了の定義を確かめる → コミット
```

### 2.1 仕様を書く

- 根拠は、取扱説明書の【確認済み】【変更】、【不具合】の本来の動き、決定事項に限る。
- 仕様の各項目に番号（§）を振る。テストとの対応に使う。
- 新しい機能や、根拠のない動きを思いついたときは、仕様に書かずに提案として分けて出す。承認されたら仕様に入れる。
- ユーザーが仕様を確認し、承認する。

### 2.2 受け入れテストを書く

- ユーザーの操作の単位（ユーザーストーリー）ごとに、Playwright の E2E テストを書く。
- 画面の要素は、ロールとラベルで探す（設計方針 §3.4）。画面の作りの細部に依存させない。
- 画面がまだないので、最初は必ず失敗する。失敗の理由が「まだ作っていないから」であることを確かめる。

### 2.3 内側の流れ

部品の種類ごとに、先に書くテストが決まっている。

| 部品 | 先に書くテスト |
|---|---|
| 競技ルール（`domain`） | 仕様のテストデータ（JSON）、性質テスト（fast-check）、単体テスト |
| 練習の進行（`application`） | 状態遷移の単体テスト。偽の時計とシード固定の乱数を使い、タイミングが絡む流れも毎回同じ結果にする |
| ポートの実装（`adapters-*`） | 契約テスト。同じポートのすべての実装が、同じテストに合格する |
| 画面の部品（`ui`） | コンポーネントテスト（Testing Library） |

1回の繰り返しは小さくする。テストを1つ書き、失敗を見て、通る最小の実装を書き、テストが通ったまま整理する。

### 2.4 完了の定義を確かめる

設計方針 §6 の完了の定義をすべて満たしたら完了とする。

## 3. テストを先に書かない例外

| 対象 | 扱い |
|---|---|
| スパイク（技術の確かめのための試作） | 捨てる前提で書く。本体には入れない。本体に必要になったら、テストを先に書いて作り直す |
| 見た目の試作 | 見た目を決めるための試作は、テストなしでよい。決まった見た目を本体に入れるときは、通常の手順に従う |
| 見た目の回帰テスト | 画面の見た目が固まってから基準画像を作る |

## 4. 仕様とテストの対応

- テストの名前に、仕様の番号を入れる。例：`仕様 01 §5.1 決まり字変化：うら の後の うか は う`
- 仕様の各項目に対応するテストがあることを、完了の前に確かめる。
- 再現手順書の不具合（B-01 など）は、「直したら確かめること」を回帰テストにし、テストの名前に番号を入れる。例：`B-24 終了後のスキップで出題が進まない`
- テストが本当に失敗できることは、テストを先に書いて失敗を見ることで確かめる。テスト全体の質は、ミューテーションテストで測る。

## 5. ブランチとコミット

- ブランチは増やさない。作り直し版の文書と実装は、すべて `rewrite` ブランチで扱う（ほかは `main` と `sample-fix` の3つだけ）。
- コミットは、テストがすべて通る状態で行う。1つのコミットには1つの意図だけを入れる。
- コミットの前に、速いチェック（書式・lint・変更したファイルの型チェック）を通す。重いチェック（ミューテーションテスト、E2E など）は CI で行う。
- GitHub への push は、ユーザーの確認を取ってから行う。

## 6. ユーザーが確認・決定するところ

| 場面 | 確認すること |
|---|---|
| 仕様書を書いたとき | 内容の承認 |
| ADR を書いたとき | 設計判断の承認 |
| 段階を終えたとき | 全体計画の完了条件を満たしているか |
| push・公開 | 実施してよいか |

## 7. AI（Claude）が実装するとき

- この文書と設計方針の要点を、リポジトリ直下の `CLAUDE.md` にまとめ、常に従う。
- 仕様にないものは作らない。思いついたものは提案として分けて出す。
- 判断に選択肢があるときは、得られるもの・増える手間・あきらめるものを先に示し、ユーザーが決める。
- 動作の確認は、実際に動かして、人に見えるもの（画面・スクリーンショット）で判断する。
