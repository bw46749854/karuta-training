# 全体計画

作り直し版を、何を、どの順番で作るかを定める。1つの機能をどう作るか（手順・テストの書き方）は [開発の進め方](workflow.md) に書く。

## 1. 前提となる決定

- **サンプルは直さない**（2026-10-31 決定）。
  - サンプルのコードは修正に弱い。決まり字の計算が3か所に別々にあり、3つとも違う間違い方をしている。設定の初期値も、画面ごとにばらばらに持っている。
  - 直しても作り直し版に引き継ぐものがない。仕様の材料は、すでに取扱説明書と再現手順書に取り出してある。
  - `sample-fix` ブランチの自動テストは、サンプルの不具合の記録として残す。
- **作り直し版の材料**
  - [取扱説明書（仕様 00）](spec/00-sample-manual.md)：【確認済み】【変更】と、【不具合】の本来の動きが、各画面の仕様の元になる。§8 は、全体に関わる決定と要検討の論点。
  - [再現手順書](spec/00-sample-repro-steps.md)：各不具合の「直したら確かめること」を、作り直し版の回帰テストにする。
  - [仕様 01 競技ルール](spec/01-karuta-rules.md)：決まり字・決まり字変化・候補集合と、そのテストデータ。
- **技術と設計**：[ADR-0001](adr/0001-technology-stack.md) と [設計方針](design/principles.md) に従う。

## 2. 順番の考え方

| 考え方 | 理由 |
|---|---|
| 危険の大きいものを先に確かめる | 起動時間が予算に入らないと、技術スタックの選び直しになる（ADR-0001 の見直し条件）。機能を作った後では手戻りが大きい |
| 守らせる仕組み（CI）を、機能のコードより先に入れる | 最初の1行から規則に従わせる。後から入れると、既存のコードの直しが大量に出る |
| 内側（競技ルール）から外側（画面）へ | 画面はルールに依存するが、ルールは画面に依存しない。ルールが固まっていれば、画面の作り直しが安く済む |
| 全体の決めごとは、画面を作る前に決める | 設定値の管理や練習モードの共通の契約は、全画面に影響する。後から変えると、作った画面すべてに手が入る |
| 画面は1つずつ、仕様からテストまで縦に仕上げる | 途中の段階でも、完成した画面が1つずつ増える。問題が早く見つかる |

この順番のトレードオフ：

- **得られるもの**：手戻りが小さい。全体の規則と決めごとの上に、画面を積み上げられる。
- **増える手間**：段階 0〜4 の間は、画面として動くものがほとんど見えない。
- **あきらめるもの**：早い段階で触れる試作品。必要なら段階 1 のスパイクで最小の画面を見ることはできるが、本体には使わない。

## 3. 段階

各段階は、完了条件を満たしてから次へ進む。段階の完了はユーザーが確認する。

### 段階 0：準備（文書）

- 設計方針を確定する。テストを先に書く方針と、未決の設計論点（取扱説明書 §8.2）を書き足す。
- 全体計画（この文書）と [開発の進め方](workflow.md) を書く。
- `CLAUDE.md` を書く。設計方針と開発の進め方の要点と、参照先をまとめる。

**完了条件**：設計方針・仕様 01・全体計画・開発の進め方が承認されている。`CLAUDE.md` がある。

### 段階 1：起動時間スパイク

- 最小の空のアプリ（Vite + React）を作り、次の場面で起動時間を計測する（予算は ADR-0001）。
  - Web 版の2回目以降の起動
  - iPad のアプリとしてのコールド起動（Capacitor）
  - Windows のアプリとしての起動（Tauri と Electron）
- スパイクのコードは捨てる。本体には使わない。

**完了条件**：計測の方法と結果、採用する包み方を ADR-0002 に記録し、承認されている。どの包み方でも予算に入らない場合は、ADR-0001 を見直す。

### 段階 2：土台

- プロジェクトの骨組み：pnpm のワークスペースで、`packages/domain`・`packages/application`・`packages/adapters-web`・`packages/ui`・`apps/web` を作る（設計方針 §2.1）。
- 守らせる仕組み（設計方針 §5）：TypeScript の設定、ESLint の規則、dependency-cruiser、knip、Prettier、コミット前のチェック。
- テストの道具（設計方針 §4）：Vitest（カバレッジの閾値）、fast-check、Stryker、Playwright、axe、size-limit。
- CI の設定。

**完了条件**：

- 空のパッケージで、すべてのチェックが通る。
- 違反するコードをわざと書くと、チェックが失敗することを確かめてある。例：`domain` から `ui` を import する、`domain` で `Date` を使う、型アサーションを使う、関数を長くしすぎる。仕組みが本当に効いていることの証明として、結果を記録する。

### 段階 3：ルールの核

`packages/domain` に、競技ルールを作る。どれも先にテストを書く。

- 歌のマスターデータと、その検証（仕様 01 §8.3）
- 静的決まり字、決まり字変化、候補集合（仕様 01）
- 決まり字グループ（仕様 01 §7）
- 答えの入力（かな・ローマ字）と判定（取扱説明書 §1.3、§2.5）。仕様 01 に書かれていない部分は、先に仕様書にする。
- 出題順の生成。乱数は引数として受け取る（`domain` は乱数を直接使わない）。
- 札の配り方（取扱説明書 §4.4。配置の初期値は §6.3）

**完了条件**：テストデータ（JSON）が全件合格。単体テストのカバレッジ 95% 以上。ミューテーションスコア 80% 以上。

### 段階 4：全体の決めごと

全画面に影響する設計を決め、ADR にする（取扱説明書 §8.2）。

| 決めること | 中身 |
|---|---|
| 設定値の管理 | どこで管理するか、依存の向き、初期値を1か所で持つこと（DRY）、変更したときの影響範囲、保存データの版とマイグレーション |
| 練習モードの共通の契約 | 練習の進行（状態遷移）の形。結果（正解・誤答・スキップ）の記録の持ち方。新しいモードを足しても、既存のモードを変えない形 |
| 文言の管理 | メッセージとボタンの文言を1か所に集める仕組みと、言い回しの基準。個々の文言は各画面で作る |
| 画面に表示する情報 | 何を表示し、何を余計とするかの基準。重複する情報（例：進捗と残り札）の扱い |
| 機器・画面の大きさ | どれくらいの粒度で分け、どこまで対応するか |

あわせて、決めた内容に沿って `application` の骨組み（ポートの定義、進行の実行器）と、`ui` の共通の枠（トップに戻るボタンなど、取扱説明書 §8.1）を作る。

**完了条件**：各 ADR が承認されている。骨組みに、設計方針どおりのテストがある。

### 段階 5：画面ごと

1つの画面ごとに、[開発の進め方](workflow.md) の手順で「仕様 → 受け入れテスト → 実装」を行う。順番と理由：

| 順番 | 画面 | 理由 |
|---|---|---|
| 1 | 札流し | ルールの核をそのまま使う、いちばん単純な画面。共通の契約を最初に試す。トップ画面は、ここで入口として最小限だけ作る |
| 2 | 札流し（複数枚） | 札流しの判定を、複数枚の問に広げる |
| 3 | 配置暗記 | 盤面（配り方・配置）が初めて出てくる |
| 4 | 実践練習 | 盤面に加えて、時間（`Clock`・`Scheduler`）が入る。いちばん難しいので最後 |
| 5 | 設定画面、トップ画面、報告・共有、リンク集 | 設定画面は、各モードの設定項目が出そろってから作る。報告の送信のまとめ方（取扱説明書 §7.2）は、報告・共有の仕様を書くときに決める |

各画面の仕様書は `docs/spec/` に、02 から番号を振って書く。

**完了条件（画面ごと）**：

- 仕様書が承認されている。
- 仕様の各項目に対応するテストがあり、すべて合格している。
- 再現手順書のうち、その画面の不具合の「直したら確かめること」が回帰テストになっている。

### 段階 6：仕上げと公開

- 文言の全体の見直し（取扱説明書 §8.2）
- 初期値の最終調整（取扱説明書 §6.5）
- 札面の差し替え（仮の画像 → 文字とフォントで組む札面。アダプタの交換だけで済むことを確かめる）
- 見た目の回帰テストの基準画像を確定する
- 公開先ごとの包み（段階 1 で決めた方式）
- 公開サイトを作り直し版に入れ替える

**完了条件**：すべてのテストとチェックが合格している。公開の判断はユーザーが行う。

## 4. 未決事項と、決める時期

| 事項 | 決める時期 |
|---|---|
| iPad でアプリとして起動時間を計測する手段。iOS のアプリを実機で動かすには、Mac と Xcode が要る | 段階 1 の前 |
| `rewrite` ブランチを GitHub に push して、CI を GitHub 上で動かすか。それまでは同じチェックを手元で動かす | 段階 2 の前 |
| 設定値の管理、練習モードの共通の契約、文言の管理、画面に表示する情報、機器・画面の大きさ | 段階 4（ADR） |
| 報告の送信のまとめ方 | 段階 5（報告・共有の仕様） |
| 初期値の値 | 段階 6 |
| 公開サイトを入れ替える方法と時期 | 段階 6 の前 |
| 正常系も含めたサンプルの動作のテスト | ユーザーの判断で保留中 |
