# 全体計画

作り直し版を、何を、どの順番で作るかを定める。1つの機能をどう作るか（手順・テストの書き方）は [開発の進め方](workflow.md) に書く。

## 1. 前提となる決定

- **サンプルは直さない**（2026-10-31 決定）。
  - サンプルのコードは修正に弱い。決まり字の計算が3か所に別々にあり、3つとも違う間違い方をしている。設定の初期値も、画面ごとにばらばらに持っている。
  - 直しても作り直し版に引き継ぐものがない。仕様の材料は、すでに取扱説明書と再現手順書に取り出してある。
  - 現行サンプルは移行元・参考として、タグ `sample`（c6423a1）で残す。サンプルの一部の修正と自動テストは、タグ `sample-fix` に不具合の記録として残す。
- **技術は ADR-0001 のとおりで確定**（2026-10-31 決定）。
  - 起動時間を測ってから技術を選ぶことはしない。この製品には、ネイティブを選ぶ理由（重い描画、音・映像、OS 固有の機能）がない。
  - React Native と Flutter は退けた。理由は ADR-0001 の「却下した選択肢」に書いた。
  - 起動時間の予算は、CI のチェックで守る（段階 1）。
- **作り直し版の材料**
  - [取扱説明書（仕様 00）](spec/00-sample-manual.md)：【確認済み】【変更】と、【不具合】の本来の動きが、各画面の仕様の元になる。§8 は、全体に関わる決定と要検討の論点。
  - [再現手順書](spec/00-sample-repro-steps.md)：各不具合の「直したら確かめること」を、作り直し版の回帰テストにする。
  - [仕様 01 競技ルール](spec/01-karuta-rules.md)：決まり字・決まり字変化・候補集合と、そのテストデータ。
- **技術と設計**：[ADR-0001](adr/0001-technology-stack.md) と [設計方針](design/principles.md) に従う。

## 2. 順番の考え方

| 考え方 | 理由 |
|---|---|
| 守らせる仕組み（CI）を、機能のコードより先に入れる | 最初の1行から規則に従わせる。後から入れると、既存のコードの直しが大量に出る |
| 内側（競技ルール）から外側（画面）へ | 画面はルールに依存するが、ルールは画面に依存しない。ルールが固まっていれば、画面の作り直しが安く済む |
| 全体の決めごとは、画面を作る前に決める | 設定値の管理や練習モードの共通の契約は、全画面に影響する。後から変えると、作った画面すべてに手が入る |
| 設定画面を、最初の画面にする | 設定は全体設計の根幹で、全モードが使う。最初に全項目で作れば、設定値の持ち方を本物の画面で確かめられる。各モードの受け入れテストも、最初から人と同じく設定画面で設定を変えられる |
| 画面は1つずつ、仕様からテストまで縦に仕上げる | 途中の段階でも、完成した画面が1つずつ増える。問題が早く見つかる |

この順番のトレードオフ：

- **得られるもの**：手戻りが小さい。全体の規則と決めごとの上に、画面を積み上げられる。
- **増える手間**：段階 0〜3 の間は、画面として動くものがほとんど見えない。
- **あきらめるもの**：早い段階で触れる試作品。最初に動く画面は、練習モードではなく設定画面になる。

## 3. 段階

各段階は、完了条件を満たしてから次へ進む。段階の完了はユーザーが確認する。

### 段階 0：準備（文書）

- 設計方針を確定する。テストを先に書く方針と、未決の設計論点（取扱説明書 §8.2）を書き足す。
- 全体計画（この文書）と [開発の進め方](workflow.md) を書く。
- `CLAUDE.md` を書く。設計方針と開発の進め方の要点と、参照先をまとめる。

**完了条件**：設計方針・仕様 01・全体計画・開発の進め方が承認されている。`CLAUDE.md` がある。

**状態**：完了（2026-10-31、ユーザー確認済み）

### 段階 1：土台

- プロジェクトの骨組み：pnpm のワークスペースで、`packages/domain`・`packages/application`・`packages/adapters-web`・`packages/ui`・`apps/web` を作る（設計方針 §2.1）。
- 守らせる仕組み（設計方針 §5）：TypeScript の設定、ESLint の規則、dependency-cruiser、knip、Prettier、コミット前のチェック。
- テストの道具（設計方針 §4）：Vitest（カバレッジの閾値）、fast-check、Stryker、Playwright、axe、size-limit。
- 性能の予算のチェック：size-limit（バンドルと素材の大きさ）と Playwright（Web 版の起動時間）を CI に入れ、空のアプリの時点から測る（ADR-0001）。
- CI の設定。すべてのチェックを1つのコマンドにまとめ、手元（WSL2）でも GitHub Actions でも同じものを動かす。

**完了条件**：

- 空のパッケージで、すべてのチェックが通る。空のアプリが、起動時間とサイズの予算に入っている。
- 違反するコードをわざと書くと、チェックが失敗することを確かめてある。例：`domain` から `ui` を import する、`domain` で `Date` を使う、型アサーションを使う、関数を長くしすぎる。仕組みが本当に効いていることの証明として、結果を文書に記録する（CI のログは保存期間が過ぎると消えるため）。

**状態**：完了（2026-10-31、ユーザー確認済み）。記録は [段階 1 の記録](records/stage-1-checks.md)。

### 段階 2：ルールの核

`packages/domain` に、競技ルールを作る。どれも先にテストを書く。

最初のテストを入れたら、テストがないときに通す設定（Vitest の `passWithNoTests`、Stryker の `allowEmpty`）を外す（[段階 1 の記録](records/stage-1-checks.md) §4）。

- 歌のマスターデータ（歌番号・静的決まり字・決まり字グループ）と、データどうしの食い違いのテスト（仕様 01 §7、§8.3）
- 決まり字変化と候補集合の計算（仕様 01 §4〜§6）
- 答えの入力（かな・ローマ字）と判定（取扱説明書 §1.3、§2.5）。仕様 01 に書かれていない部分は、先に仕様書にする（[仕様 02](spec/02-answer-input.md)）。
- 出題順の生成。乱数は引数として受け取る（`domain` は乱数を直接使わない）。
- 札の配り方（取扱説明書 §4.4。配置の初期値は §6.3）
- 出題順の生成と札の配り方は、まとめて仕様書にする（[仕様 03](spec/03-questions-and-dealing.md)）。

**完了条件**：テストデータ（JSON）が全件合格。単体テストのカバレッジ 95% 以上。ミューテーションスコア 80% 以上。

**状態**：完了（2026-11-01、ユーザー確認済み）。記録は [段階 2 の記録](records/stage-2-checks.md)。

### 段階 3：全体の決めごと

全画面に影響する設計を決め、ADR にする（取扱説明書 §8.2）。

| 決めること | 中身 |
|---|---|
| 設定値の管理 | どこで管理するか、依存の向き、初期値を1か所で持つこと（DRY）、変更したときの影響範囲、保存データの版とマイグレーション。設定画面と各画面が、設定値をどう扱うか |
| 練習モードの共通の契約 | 練習の進行（状態遷移）の形。結果（正解・誤答・スキップ）の記録の持ち方。新しいモードを足しても、既存のモードを変えない形 |
| 文言の管理 | メッセージとボタンの文言を1か所に集める仕組みと、言い回しの基準。個々の文言は各画面で作る |
| 画面に表示する情報 | 何を表示し、何を余計とするかの基準。重複する情報（例：進捗と残り札）の扱い |
| 機器・画面の大きさ | どれくらいの粒度で分け、どこまで対応するか。アプリ版の起動時間の予算を守る基準の端末 |

あわせて、決めた内容に沿って `application` の骨組み（ポートの定義、進行の実行器）と、`ui` の共通の枠（トップに戻るボタンなど、取扱説明書 §8.1）を作る。

**状態**：作業中。済み：設定値の管理（[ADR-0003](adr/0003-settings.md)）、練習モードの共通の契約（[ADR-0004](adr/0004-practice-mode-contract.md)）、文言の管理（[ADR-0005](adr/0005-wording.md)）、画面に表示する情報（[ADR-0006](adr/0006-what-screens-show.md)）、機器・画面の大きさ（[ADR-0007](adr/0007-devices-and-screen-sizes.md)）（2026-11-01）。ADR はすべて承認済み。ADR-0007 に合わせた仕様 03 §6 と盤面のコードの直しも済み（記録は [段階 3 の記録](records/stage-3-checks.md)）。残り：`application` の骨組み、`ui` の共通の枠。

**完了条件**：各 ADR が承認されている。骨組みに、設計方針どおりのテストがある。

### 段階 4：画面ごと

1つの画面ごとに、[開発の進め方](workflow.md) の手順で「仕様 → 受け入れテスト → 実装」を行う。順番と理由：

| 順番 | 画面 | 理由 |
|---|---|---|
| 1 | 設定画面（全項目） | 設定値の持ち方（段階 3）を、全項目で本物の画面にして確かめる。設定項目は取扱説明書 §6 にすべてそろっている。盤面の配置の編集（§6.3）もここで作る。トップ画面は、入口として最小限だけ作る |
| 2 | 札流し | ルールの核をそのまま使う、いちばん単純な練習モード。共通の契約を最初に試す |
| 3 | 札流し（複数枚） | 札流しの判定を、複数枚の問に広げる |
| 4 | 配置暗記 | 盤面（配り方・配置）が初めて練習に出てくる |
| 5 | 実践練習 | 盤面に加えて、時間（`Clock`・`Scheduler`）が入る。いちばん難しいので練習モードの最後 |
| 6 | トップ画面、報告・共有、リンク集 | 報告の送信のまとめ方（取扱説明書 §7.2）は、報告・共有の仕様を書くときに決める |

各画面の仕様書は `docs/spec/` に、続きの番号を振って書く（02 は答えの入力と判定、03 は出題と札の配り方なので、04 から）。各モードの仕様で設定項目の扱いが変わった場合は、設定画面の仕様と画面も一緒に直す。

**完了条件（画面ごと）**：

- 仕様書が承認されている。
- 仕様の各項目に対応するテストがあり、すべて合格している。
- 再現手順書のうち、その画面の不具合の「直したら確かめること」が回帰テストになっている。

### 段階 5：仕上げと公開

- 文言の全体の見直し（取扱説明書 §8.2）
- 初期値の最終調整（取扱説明書 §6.5）
- 札面の差し替え（仮の画像 → 文字とフォントで組む札面、または画像）。アダプタの交換だけで済むこと、CI の大きさと起動時間の予算に入ることを確かめる。
- 見た目の回帰テストの基準画像を確定する
- 公開先ごとの包み。包み方（Tauri か Electron など）は、その公開先に出すと決めたときに決める（ADR-0001）。包んだアプリが起動時間の予算に入ることを、基準の端末で確かめる。
- 公開サイトを作り直し版に入れ替える

**完了条件**：すべてのテストとチェックが合格している。公開の判断はユーザーが行う。
