# ADR-0006: 画面に表示する情報

- ステータス: 承認（2026-11-01）
- 日付: 2026-11-01

## 背景

### 決まっていること

| 決まっていること | 出どころ |
|---|---|
| 何を画面に表示すべきで、何が余計な情報か（重複や、利用者には要らない情報）を、アプリ全体で見直す | 取扱説明書 §8.2「画面に表示する情報」 |
| 札流しの「残り札」は、残りの出題枚数（進捗「n / N」の N − n）。表示し続けるかは、この見直しで決める | 取扱説明書 §2.8（確認済み）、B-21 |
| 各モードは、状態から表示用のデータを作り、`ui` はそれを表示して操作を渡すだけ | ADR-0004 論点 7 |
| 画面の言葉は、用語集に合わせる | ADR-0005 論点 4 |
| ロール・ラベル・フォーカス順などのアクセシビリティを満たす。axe で重大な違反ゼロ | 設計方針 §3.4、§4 |
| すべての操作は、コントローラーだけでも実行できるように設計する | 設計方針 §2.4 |

### 現行サンプルの画面に出ている、見直しの候補

| 画面 | 表示 | 気になる点 |
|---|---|---|
| 札流し、複数枚 | 「残り札：n 枚」 | 進捗「n / N」と同じ情報（N − n）。競技かるたで「残り札」は、陣に残っている札を指すことが多く、意味が紛らわしい |
| 設定 | 「デバッグ用 札の配置設定の配列」（テキスト欄） | 開発のための情報が、利用者に見えている（取扱説明書 §6.3） |
| 複数枚 | 判定の欄の「未開始」 | 問が出ていて、まだ答えていないときにも「未開始」と出る |

このほか、サンプルの HTML には、問の番号や状態の名前を出す部品が残っているが、隠されていて画面には出ない（コードで確認）。

関係する不具合：B-08（終了したことが表示されない）、B-19（一覧に正誤が表示されない）、B-14（盤面がないと、何も表示されずに動かない）。

## 判断の仕方

評価軸は設計方針 §1 の優先順位。

1. ルールの正しさ：画面に出ている情報が、実際の状態と合っていること。利用者が状態を取り違えないこと
2. 変更容易性：各画面の仕様（段階 4）で、同じ基準で判断できること
3. テスト容易性：表示が表示用のデータから決まり、テストで確かめられること
4. 移植性・性能：差がつかない（小さい画面で何を優先するかは、機器・画面の大きさの ADR で決める）

## 論点と決定

### 1. 何を表示するかの基準

| 選択肢 | 中身 |
|---|---|
| A | サンプルの表示を、そのまま引き継ぐ |
| **B** | **目的で選ぶ。次のどれかに役立つものだけを表示する** |

**決定：B。** 表示するのは、次のどれかに役立つものだけ。

| 目的 | 例 |
|---|---|
| 今の問に答える | 札、決まり字の文字、入力欄、盤面 |
| 結果を知る | 判定、正解、理由、決まり字一覧の正誤 |
| 進み具合を知る | 進捗「n / N」とバー |
| 次にする操作を知る | ボタン、案内のメッセージ |
| 今どの画面か、どう戻るか | 画面の見出し、トップへ戻るボタン（取扱説明書 §8.1） |

どれにも当たらないもの（開発のための情報、内部の番号や状態の名前）は表示しない。

- A では、開発のための情報や、意味の重なる情報も引き継いでしまう。段階 4 の各画面の仕様で、同じ基準で判断できるようにする。

### 2. 同じ情報を何か所に出すか

**決定：同じ情報は1か所にだけ出す。** ただし、同じ情報を形を変えて同じ場所に並べるのはよい（例：進捗の数「n / N」とバー）。

- 同じ情報が離れた所に2つあると、利用者はそれぞれ別の意味だと受け取りやすい。2つの数が食い違えば、どちらが正しいか分からなくなる（サンプルの B-21 では、進捗が「1 / 3」のときに残り札が「99 枚」と出ていた）。

### 3. 状態が変わったときと、空のとき

**決定：どの段階でも、今どうなっているかが分かる表示を出す。** 終了、出題がない、盤面がないなどの状態も含める。

- 表示は、いつも今の状態から作った表示用のデータで決まる（ADR-0004 論点 7）。表示を部分的に書き換える作りにしないので、更新の漏れ（B-08、B-19）が起きない。
- 何も表示されずに止まる、ということをなくす（B-14。盤面がないときの案内は取扱説明書 §5.4 で確認済み）。

### 4. 今できる操作の表し方

**決定：表示用のデータに「今できる操作」を含め、画面はそれに従う。** 今できない操作が、押せる見た目にならないようにする。

- 操作が意味を持つ段階は、遷移関数が決めている（ADR-0004 論点 2）。画面が独自に判断すると、遷移関数と食い違う。
- 段階で働きが変わるボタンは、1つのボタンの文言を変える（ADR-0005 論点 4）。
- 押せない操作を隠すか、押せない見た目で残すかは、各画面の仕様で決める。

### 5. 要素の役割と名前

**決定：画面の要素（ボタン、入力欄、札の画像など）に、役割（ロール）と名前を付ける。目的は次の2つ。**

| 目的 | 中身 |
|---|---|
| テスト | E2E テストは、要素を役割と名前で探す（設計方針 §3.4）。画面の作りの細部に頼らずに済む |
| キーボードとゲームパッドでの操作 | すべての操作を、コントローラーだけでもできるようにする（設計方針 §2.4。Steam 版を見込んだ決定）。それには、操作する対象を順に移れること（フォーカス順）と、今どの対象にいるかが分かることが要る |

- **画面の読み上げで練習することは、想定しない。** 練習は、札や盤面を目で見て覚えることが中心のため。役割と名前を付けると、読み上げにも副次的に役立つが、読み上げのための作り込みはしない（判定が出たことを声で知らせる、札の中身を声で伝える、など）。
- axe による基本の確認（設計方針 §4。重大な違反ゼロ）は続ける。名前の付け忘れや、役割の誤りを機械的に見つけるため。
- 名前の文言は、文言の表に入れる（ADR-0005）。

### 6. 見直しの候補への当てはめ

| 表示 | 決定 | 根拠 |
|---|---|---|
| 札流し・複数枚の「残り札」 | **表示しない** | 進捗「n / N」と同じ情報（論点 2）。用語集にない意味で「残り札」を使うことにもなり、競技かるたでの意味と紛らわしい（ADR-0005 論点 4） |
| 設定画面の「デバッグ用 札の配置設定の配列」 | **表示しない** | どの目的にも当たらない（論点 1）。札の配置は、6段×11列のチェック欄で見える |
| 複数枚の判定の欄の「未開始」 | 複数枚の仕様で、この基準に当てはめて決める | 判定の欄の出し方は、画面の仕様の範囲 |

## この ADR で決めないこと

| 事項 | 決める所 |
|---|---|
| 各画面に何を、どこに、どう出すか | 各画面の仕様（段階 4）。この ADR の基準に従う |
| 文言 | 各画面の仕様（ADR-0005） |
| 小さい画面で、何を優先して残すか | 機器・画面の大きさの ADR |
| 押せない操作を隠すか、押せない見た目で残すか | 各画面の仕様 |

## 却下した選択肢

| 選択肢 | 退けた理由 |
|---|---|
| サンプルの表示をそのまま引き継ぐ | 開発のための情報や、意味の重なる情報も引き継ぐ |
| 同じ情報を別の場所に重ねて出す | 別の意味だと受け取られやすく、片方の更新漏れで食い違って見える |
| 今できる操作を、画面が独自に判断する | 遷移関数と食い違う |

## 範囲と制約

### 標準でできること

- 各画面の仕様で、表示するものを同じ基準で選べる。
- 表示の更新漏れが、作りの上で起きない。

### 諦めること

- 「残り札」の表示。進捗「n / N」から読み取る。
- 画面の読み上げだけで練習すること（論点 5）。

## この決定を見直す条件

- 利用者から、表示しないことにした情報（「残り札」など）を求める声が出たとき。
- 画面の読み上げで使いたいという求めが出たとき（どの練習なら読み上げで成り立つかから考える）。
- 機器・画面の大きさの ADR で、小さい画面で出す情報を絞る基準が要るとき（この ADR の目的の順に、優先度を付ける）。
