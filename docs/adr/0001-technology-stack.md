# ADR-0001: 技術スタック

- ステータス: 承認
- 日付: 2026-10-30

## 背景

既存の実装（素の HTML/JS）は「作りたいもの」を示すサンプルとして扱い、全面的に作り直す。
サンプルから読み取った要件は次のとおり。

| 観点 | 実態 |
|---|---|
| 画面 | 札流し、複数枚・札認識、配置暗記（6×11 の盤面）、実践練習（決まり字を1文字ずつ表示して札を取る）、設定、報告フォーム、リンク集 |
| 入力 | タップ、日本語のかな入力（IME）、ローマ字入力 |
| 時間制御 | 文字間隔・待機時間・出現時間、反応時間の計測（ミリ秒単位）。音声はなし |
| 描画 | 2D のカード最大66枚。物理演算・3D・高フレームレートは不要 |
| 本質的な難しさ | 決まり字変化・ローマ字変換・札の配分・出題の進行といった競技ルールの正しさ |
| 外部連携 | 端末内への保存、報告送信（Google Apps Script） |

将来の公開先として Web・iPad（iOS）・Android・PC（exe）・Steam が挙がっている。

## 評価軸

| 軸 | 重み | 理由 |
|---|---|---|
| ルールの正しさと変更容易性（型・テスト） | 最重要 | アプリの価値の中心 |
| 日本語入力・日本語組版・タッチ操作の質 | 高 | 札流しは「かなで答える」のが中心 |
| E2E テストのしやすさ | 高 | 品質を仕組みで担保する |
| 1つのコードで複数の公開先に出せるか | 高 | 公開先の候補が多い |
| 長期保守性（エコシステムの安定、学習コスト） | 中 | |
| 性能 | 低 | 要件が軽い。ただし起動時間は別途予算で管理する（後述） |
| メモリ安全性 | 差がつかない | TypeScript/JavaScript は GC 言語でもともとメモリ安全 |

## 決定

**Web ファースト。TypeScript（strict）+ Vite + React で作り、各公開先へは同じコードを包んで出す。**

| 層 | 選定 |
|---|---|
| 言語・ビルド | TypeScript（strict）、Vite、pnpm（ワークスペース）。バージョンは着手時点の最新安定版で固定 |
| ルール層 | 純粋な TypeScript。時計・乱数・保存先などはポート（インターフェース）として外から注入。乱数はシード指定可能 |
| UI | React（React への依存は UI 層だけ）、CSS Modules |
| 入力値の検証 | スキーマ検証ライブラリ（Valibot などバンドルの小さいもの） |
| テスト | Vitest、fast-check（プロパティベーステスト）、Testing Library、Playwright（Chromium / WebKit / Firefox）、Stryker（ミューテーションテスト） |
| 品質ゲート | `tsc`、typescript-eslint（strict-type-checked）、dependency-cruiser、knip、size-limit、GitHub Actions |
| 配布 | Web（PWA）→ iOS/Android（Capacitor）→ PC/Steam（Tauri または Electron。Steam 対応時に決定） |

詳細な設計方針と、それを守らせる仕組みは [設計方針](../design/principles.md) に定める。

## 却下した選択肢

| 候補 | 理由 |
|---|---|
| 現状維持（素の JS） | 型・モジュール・テスト基盤がなく、品質を仕組みで担保できない |
| three.js / PixiJS を土台にする | 3D・大量描画は要件にない。canvas の中身は E2E で要素として扱えない。演出が必要になれば局所的に追加する |
| Bevy | 1.0 前で破壊的変更が続く。UI 部品と日本語テキスト入力（IME）の自作比重が大きい。iOS・WASM 出力が主流でない。E2E 基盤も自作になる |
| Unity / Godot / Defold | 家庭用ゲーム機には強いが、Web 版の質・日本語入力・UI の E2E テストで不利。ゲーム機を対象外とした（後述）ため採用理由がない |
| Flutter | 次点。Web 版が canvas 描画で、日本語入力と初回ロードで不利 |

## 範囲と制約

### 標準でできること
- 1つのコードで Web（PWA）・iOS/iPadOS・Android・Windows・Mac・Linux・Steam（Steam Deck 含む）に配布
- 日本語 IME、縦書き、VoiceOver などのアクセシビリティ
- オフライン動作
- タッチ・マウス・キーボード操作
- ルール層から E2E まで全層の自動テスト

### 追加実装でできること（実施するかは別途判断）
- Steam の実績・統計・ランキング・クラウドセーブ（クラウドセーブは Auto-Cloud なら設定のみ）
- ゲームパッド操作
- 振動フィードバック、アプリ内課金、通知
- オンライン対戦（サーバーが別途必要）

### 制約がある・事前検証が必要なこと
- 端末ごとの WebView 差（Chromium 系 / WebKit / WebKitGTK）。3エンジンの E2E で吸収するが、完全一致は保証しない
- iOS/Android の日本語キーボードの挙動差。アプリ内かなキーパッドで OS の IME 依存を外せる
- Steam Deck のゲームモードでのかな入力は要検証。ローマ字入力で代替できる
- App Store 審査（ガイドライン 4.2「最低限の機能」）。通過は保証できない
- ブラウザのタイマーの揺らぎ（数ミリ秒）。0.01 秒単位の計測は可能だが、フレーム単位の厳密さは保証しない
- TypeScript の型には抜け道がある。strict 設定・lint・境界での実行時検証で補うが、Rust と同等の保証はない

### 諦めること
- 家庭用ゲーム機での発売
- 本格的な 3D 表現や大量のパーティクルなどのリッチな演出
- Steam オーバーレイの安定動作
- ネイティブの理論上最速の起動時間の保証（ただし起動時間は予算で管理する。後述）
- Game Center やウィジェットなど OS 固有機能（計画外。プラグインで後付けは可能）

## 家庭用ゲーム機について

対象外とする。ただし将来の移植に備えて、次の2点を設計に組み込む（コストは小さい）。

1. **ルールのテストケースを言語非依存のデータ（JSON）として持つ。** 移植時は同じデータで移植先のルール実装を検証できる。
2. **入力を抽象化し、コントローラーだけで全操作できる UI にする。** Steam Deck 対応にもそのまま効く。

## 起動時間の予算

起動時間は「諦める」ものではなく、予算を決めて守る要件とする。2秒かかる状態は許容しない。

| 場面 | 予算 |
|---|---|
| Web 版の2回目以降の起動 | 0.5 秒以内に操作可能 |
| iOS/Android アプリのコールド起動 | 1 秒以内（実機で計測して確定） |
| バックグラウンドからの復帰 | 即時 |
| PC/Steam 版の起動 | 1 秒以内 |

機能開発の前に、iPad と Windows で空のアプリの起動時間を計測するスパイクを行う。予算に収まらなければ包み方（Tauri / Electron / Capacitor）を選び直す。

## この決定を見直す条件

- 家庭用ゲーム機での発売が決まったとき
- 本格的な 3D 表現が必須になったとき
- 起動時間のスパイクが、どの包み方でも予算に収まらなかったとき
