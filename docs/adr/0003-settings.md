# ADR-0003: 設定値の管理

- ステータス: 承認（2026-11-01）
- 日付: 2026-11-01

## 背景

### 設定とは

- **全モードで共通の項目**：出題の範囲（「決まり字を限定する」と選んだ歌。取扱説明書 §6.2）、札の配置（§6.3）。
- **モードごとの項目**：札流し（§2.3）、複数枚（§3.3）、配置暗記（§4.3）、実践練習（§5.3）の各表。
- 編集するのは設定画面だけ。保存先は端末の中。

### 決まっていること

| 決まっていること | 出どころ |
|---|---|
| 設定画面の初期値と、各モードが実際に使う初期値を一致させる。値は段階 5 で調整する。札の配置の初期値（各陣 25 マス）は決定済み | 取扱説明書 §6.5、§8.1、B-26、B-27 |
| 設定画面の「リセット」は、画面の値を初期値に戻すだけで、保存しない。「保存」で保存する。保存せずにトップへ戻ったら、変更を破棄する | 取扱説明書 §6.4、§8.1 |
| 選んだ歌と「決まり字を限定する」は、全モードで共通 | 取扱説明書 §6.2 |
| 保存データは境界で検証する。版を持ち、変更するときはマイグレーションの関数とテストを書く | 設計方針 §3.3 |
| 保存先は `SettingsRepository` ポートを通す。公開先ごとに実装を替える | 設計方針 §2.2 |

### 現行サンプルの問題（コードで確認）

| 不具合 | 原因 |
|---|---|
| B-26 設定画面の初期値と、各モードの初期値が違う | 各モードのファイルが、それぞれ自分の初期値を書いている |
| §6.4 「限定する」を OFF で保存しても、次に開くと ON に戻る | 設定画面は「限定する」をモードごとの欄に保存し、読み込むときは共通の欄から読む。書いていない所から読んでいる |
| B-03 複数枚がローマ字を受け付けない | 複数枚は、始めるときは `judgeByRomaji` を読み、やり直すときは、どこにも保存されていない `isRomanized` を読む |

サンプルは、すべての設定を1つの保存データにまとめている。ただし、共通の項目（限定する・選んだ歌・札の配置）を、モードごとの欄に写して重ねて持っている。

3つの不具合の共通の原因は、**項目の名前と初期値が、ファイルごとに別々に書かれていること**。

## 判断の仕方

評価軸は、設計方針 §1 の品質特性の優先順位。

1. ルールの正しさ：画面に出ている設定のとおりに、各モードが動くこと
2. 変更容易性：項目の追加や変更が1か所で済み、影響範囲が読めること
3. テスト容易性：画面を動かさずに、設定の振る舞いを確かめられること
4. 移植性：保存先を、公開先ごとに替えられること
5. 性能：設定は小さいので、差がつかない

軸で差がつかなければ、費用と、後で変えるときの費用で決める。

## 論点と決定

### 1. 設定の定義（項目・型・範囲・初期値）を、何か所に、どう書くか

この論点には、2つの問いが含まれる。「定義をどう書くか」と「設定画面を定義から自動で作るか」。分けて決める。

| 選択肢 | 中身 |
|---|---|
| A | 設定画面と各モードが、それぞれ定義を持つ（サンプル） |
| B | 1か所の定義。項目ごとに、型・初期値・検証を、それぞれ手で書く |
| **C** | **1か所の宣言的な定義。項目の種類（ON/OFF、範囲のある整数、選択肢、歌の集まり、札の配置）を組み合わせて1行ずつ書き、型・初期値・検証をその記述から作る** |
| D | C に加えて、設定画面も定義から自動で作る |

**トレードオフ**：

- A と、B〜D：食い違わないこと。
- B と C：書く手間はほぼ同じ。違いは、1つの項目を何か所に書くか。
- C と D：違いは手間よりも、画面の形の自由さ。画面の都合を、定義に持たせるかどうか。

**決定：C。設定画面の自動生成（D）は、設定画面の仕様を書くとき（段階 4）に決める。**

- **A を退ける理由**：サンプルの3つの不具合は、どれも A の構造から来ている。1か所の定義なら、項目名の書き間違いは型の誤りとして止まり（B-03、§6.4）、初期値は1つしかないので食い違えない（B-26 が構造の上で起きない）。
- **B ではなく C にする理由**：手間はほとんど変わらない。項目ごとの記述は1行で、種類ごとの検証の部品は5つほど。B は1つの項目について、型・初期値・検証の3か所を書くので、項目を足すときに書き漏らしが起こりうる（初期値だけ足して検証を忘れる、など）。C なら1か所で済む。
- **D を今決めない理由**：
  - 歌の選び方の一覧と、札の配置の編集は、D でも専用の部品が要る。自動で作れるのは、ON/OFF・範囲のある整数・選択肢の、単純な項目だけ。
  - 項目の並び・まとめ方・ほかの項目によって出し入れする項目（例：「自動で次へ進む」が OFF のときの待機時間）を自動生成で扱うには、それを定義に持たせることになり、定義が画面の都合で太る。
  - 画面の形は、設定画面の仕様を書くまで分からない。分かってから決めても、手戻りは小さい（下記）。
- **設定画面の作り方（D にしない間）**：定義の項目を受け取る共通の入力部品（ON/OFF、範囲のある整数、選択肢）を並べて組み立てる。範囲と選択肢は、定義から取る。
- **後から D にするときの手戻り**：設定画面の、部品を並べている所だけ。定義・検証・保存・テストは変わらない。
- **D の主な利点を、テストで得る**：定義のすべての項目が、設定画面に入力欄を持つことを、設定画面のテストで確かめる。画面に出し忘れた項目を見つけられる。
- 範囲（最小・最大）と選択肢は定義に持ち、検証と入力部品の両方がそれを使う。範囲を二重に書かない。
- 文言（項目の名前の表示など）は定義に持たない。文言の管理の ADR で決める。
- 定義を書くための部品は、自分で書く。検証のライブラリ（zod など）は実行時の依存が増え、`application` が外部のライブラリを使えない規則（設計方針 §2.1）にも当たる。必要な部品は5つほどで足りる。

### 2. 定義をどの層に置くか（依存の向き）

| 選択肢 | 退けた／選んだ理由 |
|---|---|
| `domain` | 設定は競技ルールではなく、練習の進め方の好み。ただし値の種類は `domain` の型を使う（札の向き、出題モード、札の配置、歌番号） |
| **`application`** | **設定画面・各モードの画面（`ui`）・保存のアダプタが、すべて内側を向く** |
| `ui`（設定画面） | 各モードの画面と `application` の進行が、設定画面に依存する。依存の向きが逆になる |
| 専用のパッケージ | `application` と同じ位置に層をもう1つ作るだけで、得るものがない |

**決定：`application` に置く。**

```
  ui（設定画面）     ui（各モードの画面）
          ↘           ↙
  application：設定の定義・初期値・検証・編集・SettingsRepository ポート
          ↑ 実装               ↓ 値の種類
  adapters-web（保存）         domain
```

### 3. 保存の単位

| 選択肢 | 中身 |
|---|---|
| **A** | **すべての設定を1つの文書にする。版の番号を持つ** |
| B | モードごとに分けて保存する |
| C | 項目ごとに保存する |

**トレードオフ**：まとめて一度に書けること、に対して、一部だけを書き換える細かさ。

**決定：A。** 中は「共通」（出題の範囲、札の配置）と、モードごとの欄に分ける。共通の項目は1回だけ持つ。

- 設定画面はまとめて保存する（§6.4）。全体を一度に書けば、途中まで書いた状態が残らない。版も1つで済む。
- B と C は、共通の項目を重ねて持つか（サンプルの §6.4 の不具合の元）、書いている途中で一部だけ変わった状態を生む。
- 盤面（配置暗記から実践練習へ渡す並び）は、設定ではない別の保存データにする（`BoardRepository`）。書く時機も使う画面も違うため。

### 4. 読み込んだデータに、項目がない・値が壊れているとき

| 選択肢 | 中身 |
|---|---|
| A | どれか1つでも不正なら、全体を初期値に戻す |
| **B** | **項目ごとに確かめ、ない項目や不正な項目だけを初期値で補う** |

**トレードオフ**：書くことの少なさ、に対して、利用者の設定を守ることと、項目の足しやすさ。

**決定：B。**

- 1つの項目の不正で、ほかの設定まで失わない。
- 新しい項目を足したとき、古い保存データにはその項目がないが、初期値で補えるので、版を上げずに済む（変更容易性）。
- 知らない項目は捨てる。
- 一度も保存していないときは、全項目が初期値になる。これは設定画面の初期値と同じもの（B-26）。

### 5. 保存先との境目と、版・マイグレーション

| 選択肢 | 中身 |
|---|---|
| A | ポートが、検証済みの設定を返す（検証はアダプタが行う） |
| **B** | **ポートは保存した文書をそのまま出し入れし、検証とマイグレーションは `application` が行う** |

**決定：B。**

- 検証とマイグレーションは、公開先（Web、アプリ、Steam）と関係がない。`application` に1つ書けば、アダプタは読み書きだけになり、公開先を増やすときに検証を書き直さなくてよい。
- 純粋な関数になるので、壊れたデータ・古い版・欠けた項目を、保存先なしでテストできる。
- **版**：文書に版の番号を持たせる。互換のない変更（項目の名前や意味の変更、値を移す必要のある削除）のときだけ版を上げ、古い版を新しい版に直す関数を1つずつ足し、テストを書く。項目の追加では版を上げない（論点 4）。

### 6. 設定画面での編集（下書き・リセット・保存・破棄）

| 選択肢 | 中身 |
|---|---|
| A | 画面（`ui`）の中だけで持つ |
| **B** | **`application` が、編集中の値（下書き）と保存済みの値を持ち、操作を状態遷移として書く** |

**決定：B。** 操作は、項目を変える、初期値に戻す、保存する、破棄する、の4つ。`ui` は表示と操作の発行だけを行う。

- §6.4 の決定（リセットは保存しない、保存せずに戻れば破棄）は、振る舞いのルール。画面なしでテストでき、設計方針の「`ui` はルールの計算をしない」にも合う。

### 7. 各モードへの渡し方

| 選択肢 | 中身 |
|---|---|
| A | 各モードが、保存先を直接読む |
| **B** | **モードを始めるときに `application` が読み、そのモードに要る分だけを渡す。その回のあいだは変わらない** |
| C | 設定の変化を、動いている練習にも反映する |

**決定：B。**

- モードは保存先を知らなくてよい（移植性、テスト容易性）。要る分だけを受け取る（インターフェース分離）。
- 練習の途中で設定を変える操作はない（設定画面は別の画面）ので、C の仕組みは要らない。

### 8. 不正な値を表せない型

**決定：設定の値は、検証を通ったものしか作れない型にする**（設計方針 §3.2）。作り方は、初期値、保存データの読み込み、編集の操作の3つだけにする。

- 範囲の外の値（例：待機時間 0 ミリ秒）や、ありえない組み合わせを、モードが受け取ることがなくなる。

## 変更の影響範囲

| 変更 | 直す所 |
|---|---|
| 項目を足す | 定義（型・範囲・初期値）、設定画面、使うモード。保存データの版は上げない |
| 初期値を変える | 定義の1か所（段階 5 で調整する） |
| 範囲を変える | 定義の1か所。範囲の外になった保存値は、読み込みのときに初期値で補われる |
| 項目の名前や意味を変える、削除する | 定義、設定画面、使うモード。版を上げ、マイグレーションの関数とテストを足す |
| 保存先を替える（アプリ版、Steam Cloud など） | アダプタだけ |

## テスト

- 初期値が、定義の検証を通ること。
- 定義のすべての項目が、設定画面に入力欄を持つこと（設定画面のテスト。段階 4）。
- 読み込み：一度も保存していない、項目がない、値が範囲の外、型が違う、知らない項目がある、壊れた文書、の各場合。
- マイグレーション：版ごとに、古い文書が新しい文書になること。
- 編集：リセットしても保存されない、保存すると保存済みの値が変わる、破棄すると保存済みの値に戻る。
- 保存のアダプタ：契約テスト（同じポートのすべての実装が、同じテストに合格する。設計方針 §3.1）。

## この ADR で決めないこと

| 事項 | 決める所 |
|---|---|
| 設定項目の一覧と、各項目の意味 | 設定画面と各モードの仕様（段階 4）。今わかっている項目は、取扱説明書の各章の表 |
| 初期値の値 | 段階 5。札の配置は決定済み |
| 設定画面の作りと文言 | 設定画面の仕様と、文言の管理の ADR |
| 保存せずに離れるとき、確かめるかどうか | 設定画面の仕様 |
| サンプルの保存データを引き継ぐか | 公開サイトの入れ替えを決めるとき（全体計画 §4）。この ADR では引き継がない形で作る。引き継ぐと決めたら、サンプルの形から読む変換を1つ足す |

## 却下した選択肢

| 選択肢 | 退けた理由 |
|---|---|
| 設定画面と各モードが、それぞれ定義を持つ（サンプル） | 項目名と初期値が食い違う。サンプルの3つの不具合の原因 |
| 1か所の定義に、型・初期値・検証を項目ごとに手で書く | 宣言的に書くのと手間はほぼ同じで、1つの項目を3か所に書くので書き漏らしが起こりうる |
| 設定画面も、今の時点で定義から自動で作る | 画面の形が分からない今、画面の都合を定義に持たせることになる。設定画面の仕様を書くときに決める（論点 1） |
| 定義を `domain` か `ui` に置く | `domain`：競技ルールではない。`ui`：依存の向きが逆になる |
| モードごと・項目ごとに保存する | 共通の項目が重なるか、一部だけ変わった状態が残る |
| 1つでも不正なら全体を初期値に戻す | ほかの設定まで失う。項目を足すたびに版を上げることになる |
| 検証をアダプタで行う | 公開先ごとに同じ検証を書くことになる |
| 練習中の設定の変化を反映する | 練習中に設定を変える操作がない |

## 範囲と制約

### 標準でできること

- 設定画面の初期値と、各モードの初期値が、構造の上で一致する。
- 項目の追加が、版を上げずにできる。
- 保存先を、アダプタの交換だけで替えられる。

### 追加実装でできること（実施するかは別途判断）

- 設定の書き出しと読み込み（ほかの端末へ移す）。
- 複数のタブで同時に編集したときの調整。

### 諦めること

- 複数のタブで設定を同時に変えて保存したときは、後で保存した方だけが残る。
- サンプルの保存データは、今は引き継がない（「この ADR で決めないこと」のとおり、後で決める）。

## この決定を見直す条件

- 設定画面の仕様を書くとき（段階 4）。画面の形が項目の並びどおりで済むなら、設定画面を定義から自動で作る（論点 1 の D）。
- 設定項目が大きく増え、設定画面に部品を並べる手間がつらくなったとき（同じく D を考える）。
- 端末をまたいだ同期（Steam Cloud など）で、同時に編集したときの食い違いが問題になったとき。
- 練習の途中で設定を変える機能を入れるとき。
