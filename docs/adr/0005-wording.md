# ADR-0005: 文言の管理

- ステータス: 承認（2026-11-01）
- 日付: 2026-11-01

## 背景

### 文言とは

画面に出る言葉のすべて。ボタン、見出し、設定項目の名前、判定の表示、理由、案内、エラー、要素の名前（画像の名前など。テストとコントローラーでの操作のために付ける。ADR-0006 論点 5）。

### 決まっていること

| 決まっていること | 出どころ |
|---|---|
| 画面の文言は1か所に集める（将来の多言語化と、テストでの参照のため） | 設計方針 §3.4 |
| E2E テストは、画面の要素をロールとラベルで探す | 設計方針 §3.4、開発の進め方 §2.2 |
| 判定の理由、エラー、案内などの文言は、1か所ずつではなく、アプリ全体を通して管理する | 取扱説明書 §8.2「メッセージの管理」 |
| ボタンの文言は、アプリ全体で統一して見直す | 取扱説明書 §8.2「ボタンの文言」 |
| 配置暗記の判定前のボタンは、「次へ進む」ではなく、問を飛ばすことが分かる文言にする | 取扱説明書 §4.6（変更） |
| 表示する理由は、入力した内容に合わせる | B-22 |
| 個々の文言は各画面で作り、段階 5 で全体を見直す | 全体計画 段階 3、段階 5 |

### 文言を待っているもの

- かなに直せない理由の4種類（仕様 02 §5）
- 複数枚で受け付けない入力（区切りだけ、答えが多すぎる）のメッセージ（仕様 02 §7）
- 実践練習で盤面がないときのメッセージ（取扱説明書 §5.4）
- 判定前に問を飛ばすボタン（取扱説明書 §4.6、§5.8）

### 現行サンプルの問題

| 問題 | 中身 |
|---|---|
| 文言が各画面のコードに直接書かれている | 同じ働きのボタンが画面ごとに違う言葉になる（「次へ」「次へ進む」）。段階で働きが変わるのに文言が変わらない（配置暗記の「次へ進む」、実践練習の「次へ進む」） |
| 理由が入力と合わない | カタカナを入力しても「ローマ字表記が仕様外」と出る（B-22） |
| 文字化け | 送信のエラーメッセージが、コードの中で化けたまま書かれている（B-18） |

## 判断の仕方

評価軸は設計方針 §1 の優先順位。

1. ルールの正しさ：利用者に伝わる内容が、実際の動き（判定の理由、ボタンを押して起きること）と合っていること
2. 変更容易性：文言を直すのが1か所で済み、テストを直さなくてよいこと。言語を足せる形であること
3. テスト容易性：テストが文言の表を通して要素を探せること。文言の抜けを機械的に見つけられること
4. 移植性：内側の層（`domain`・`application`）が、言語に縛られないこと
5. 性能：差がつかない（実行時の依存を増やさない）

## 論点と決定

### 1. 文言をどこに、どう集めるか

| 選択肢 | 中身 |
|---|---|
| A | 各画面のコードに直接書く（サンプル） |
| **B** | **1か所の文言の表を、型付きで持つ（TypeScript のオブジェクト）。画面とテストは、表の項目を参照する** |
| C | 多言語化のライブラリ（i18next など）を使う |

**決定：B。** 表は `ui` に置く。全画面で共通の文言（よく使うボタン、共通のメッセージ）と、画面ごとの文言に分ける。

- 文言を直すのが1か所で済む。テストは表を参照して要素を探すので、文言を直してもテストは直さなくてよい。
- 型付きなので、表にない項目を参照すると型の誤りになる。
- C は、複数の言語や、数による言い回しの変化（英語の単数・複数など）を扱えるが、実行時の依存が増える。今は日本語だけなので要らない。言語を足すと決めたときに考える（論点 6）。

### 2. 内側の層と文言の関係

| 選択肢 | 中身 |
|---|---|
| A | `application` が、画面に出す文字列を返す |
| **B** | **`domain` と `application` は「何が起きたか」の種類（判定の結果、理由のコードなど）を返し、`ui` が文言の表で文字列にする** |

**決定：B。**

- 内側の層が言語に縛られない（言語を足しても、ルールと進行のコードは変わらない）。
- 種類から文言への対応を、種類ごとに漏れなく書く形にする（例：かなに直せない理由の4種類それぞれに文言）。種類を足したのに文言を書き忘れると、型の誤りになる。
- 種類が細かく分かれているので、理由を入力に合わせられる（B-22）。

### 3. 値の入る文言

| 選択肢 | 中身 |
|---|---|
| A | 文言に穴（例：`正解は {kimariji}`）を書き、実行時に埋める |
| **B** | **値の入る文言は、値を受け取って文字列を返す関数にする（例：決まり字を受け取って「正解は ○○」を返す）** |

**決定：B。**

- 入れる値の名前と型が、型で確かめられる。穴の名前の書き間違いが起きない。
- 数の書き方（例：ずれの秒数を小数第2位まで）も、その関数の中に1か所で書ける。

### 4. 言い回しの基準

**決定：次の基準に従う。** 個々の文言は各画面の仕様で決め、段階 5 で全体を見直す。

| 基準 | 中身 |
|---|---|
| ボタンは、押したときに起きることを書く | 短い言葉で。段階によって働きが変わるなら、文言も変える（例：判定前は問を飛ばす文言、判定後は次へ進む文言）。取扱説明書 §4.6 の決定を、全画面に広げたもの |
| 同じ働きには、同じ言葉 | 全画面で揃える。共通の文言として表に1つだけ持つ |
| メッセージは、起きたことと、次にすること | 何が起きたかを書く。利用者がすることがあれば、それも書く（例：盤面がないとき、配置暗記へ移る案内） |
| 理由は、入力に合わせる | 種類ごとに文言を分ける（論点 2、B-22） |
| 用語は、用語集に合わせる | 仕様 01 §2 の用語（決まり字、空札、出札など）を使う |
| 文体 | 案内とメッセージは「です・ます」。ボタン・見出し・項目名は、短い言い切りの形 |

### 5. 文言を決める流れと、テスト

**決定**：

- 文言は、各画面の仕様に書いて承認を受け、文言の表に写す。仕様と表が食い違ったら、仕様を正とする。
- E2E テストとコンポーネントのテストは、文言の表を参照して要素を探す。
- 文言の表について、次をテストで確かめる。
  - 文言に、文字化けの印（置き換え文字「�」）がない（B-18 の種類の不具合）。
  - 種類から文言への対応に、抜けがない（型で確かめる）。

### 6. 多言語化

**決定：今は日本語だけにする。** ただし、文言の表は、言語ごとに同じ形（同じ型）の表を足せば済む作りにしておく。

- 言語を足すと決めたときに、言語の切り替え方、数による言い回しの変化、ライブラリを使うかを、ADR で決める。
- 内側の層は文言を持たない（論点 2）ので、言語を足してもルールと進行のコードは変わらない。

## この ADR で決めないこと

| 事項 | 決める所 |
|---|---|
| 個々の文言 | 各画面の仕様（段階 4）。全体の見直しは段階 5 |
| 何を画面に表示するか | 画面に表示する情報の ADR |
| 札の画像の名前など、要素の名前の文言の細部 | 各画面の仕様（文言の表に入れることは、この ADR で決めた） |

## 却下した選択肢

| 選択肢 | 退けた理由 |
|---|---|
| 各画面のコードに直接書く | 同じ働きの言葉が食い違う。文言を直すとテストも直すことになる |
| 多言語化のライブラリを今入れる | 実行時の依存が増える。日本語だけの今は要らない |
| `application` が画面に出す文字列を返す | 内側の層が言語に縛られる |
| 文言に穴を書いて、実行時に埋める | 穴の名前の誤りが、型で見つからない |

## 範囲と制約

### 標準でできること

- 文言を1か所で直せる。テストを直さなくてよい。
- 理由やボタンの文言の抜けを、型で見つけられる。

### 追加実装でできること（実施するかは別途判断）

- 言語を足す（同じ形の表を足し、切り替え方を決める）。

### 諦めること

- 今は、日本語のほかの言語で表示すること。

## この決定を見直す条件

- 言語を足すと決めたとき（切り替え方、言い回しの変化、ライブラリを ADR で決める）。
- 文言の量が大きく増え、表の分け方がつらくなったとき。
