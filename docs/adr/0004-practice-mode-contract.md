# ADR-0004: 練習モードの共通の契約

- ステータス: 承認待ち
- 日付: 2026-11-01

## 背景

### 4つの練習モード

| モード | 1問の流れ（取扱説明書） | 時間の扱い |
|---|---|---|
| 札流し | 札を出す → 答える（またはスキップ）→ 判定 → 次へ（自動または「次へ」） | 自動で次へ進むまでの待機時間 |
| 札流し（複数枚） | 札を出す → 出現時間の後に伏せる → 1行で答える（またはスキップ）→ 判定 → 次へ | 出現時間、待機時間 |
| 配置暗記 | 覚える時間（札を裏返す、表示反転、リセット）→ 出題 → マスを選ぶ → 回答 → 判定 → 正解札の表示と確認 → 次へ | 待機時間 |
| 実践練習 | 決まり字を1文字ずつ出す → 札を取る（最初の1回だけ有効）→ 判定（タイミング）→ 次へ | 文字間隔、取った時刻、待機時間 |

共通するのは、問を順に出す、答えを受け取って判定する、結果（正解・誤答・スキップ）を記録する、次の問へ進む（自動または手動）、終わる、の流れ。違うのは、問の中身、答え方、時間の使い方、配置暗記の「覚える時間」のような前段。

### 決まっていること

| 決まっていること | 出どころ |
|---|---|
| 進行は `(状態, イベント) → (新しい状態, 副作用の指示)` という純粋な遷移関数で表し、副作用はデータで返す。実行は外側 | 設計方針 §2.3 |
| 新しいモードを足しても、既存のモードを変えない | 設計方針 §3.1、全体計画 段階 3 |
| 入力は、デバイスではなく意味のあるコマンドで受け取る | 設計方針 §2.4 |
| 時刻・予約（タイマー）・乱数・保存は、ポートを通す | 設計方針 §2.2、ADR-0002 |
| 答えずに先へ進んだ問は、正解・誤答とは別の「スキップ」として記録する（全モード） | 取扱説明書 §8.1 |
| 設定は、モードを始めるときに、そのモードに要る分だけを受け取る | ADR-0003 論点 7 |

### 現行サンプルの、進行に関わる不具合

| 種類 | 不具合 |
|---|---|
| ある状態で効いてはいけない操作が効く、または要る操作がない | B-24（終了後も「スキップ」が効く）、B-04（判定の後、次の問へ進めない）、B-08（終了したことが表示されない） |
| 前の問の何かが、次の問に残る | B-16（読んでいる途中で次へ進むと、前の問のタイマーが残って判定が狂う）、B-07（前の問の札が表のまま残る）、B-13（リセットしても裏のまま残る札がある） |
| 結果が残らない | B-19（スキップした札が記録されない） |

サンプルは、各画面が状態を変数と旗（`advanced`、`awaitingNext` など）でばらばらに持ち、タイマーを画面の中で直接使っている。

## 判断の仕方

評価軸は設計方針 §1 の優先順位。

1. ルールの正しさ：上の3種類の不具合が、構造の上で起きないこと
2. 変更容易性：モードを足しても、既存のモードと共通部分を変えないこと
3. テスト容易性：時間が絡む流れも、実際の時間を待たずに、毎回同じ結果で確かめられること
4. 移植性：入力デバイスや公開先が変わっても、進行のコードが変わらないこと
5. 性能：差がつかない（実行時の依存を増やさない）

## 論点と決定

### 1. 進行の表し方

| 選択肢 | 中身 |
|---|---|
| **A** | **純粋な遷移関数。状態とコマンドを受け取り、新しい状態と、副作用の指示（データ）を返す（設計方針 §2.3）** |
| B | 状態と処理を持つオブジェクトにし、タイマーも中で使う（サンプルに近い） |
| C | 状態遷移のライブラリ（XState など）を使う |

**決定：A。**

- 時間が絡む流れ（特に実践練習）を、偽の時計で、実際の時間を待たずに、毎回同じ結果で確かめられる。
- B は、サンプルの不具合（B-16 など）が生まれた形。タイマーと状態が混ざり、前の問の処理が残りやすい。
- C は状態遷移を図にできるが、実行時の依存が増え、4つのモードの規模には見合わない。A で足りる。

### 2. 状態と、受け付ける操作

**決定：各モードの状態を、段階（例：出題中・判定後・終了）を区別できる型（判別可能なユニオン型）で表す。各コマンドは、それが意味を持つ段階でだけ扱い、ほかの段階では何もしない（状態を変えない）。**

- 「終了後のスキップ」（B-24）のような、ありえない操作は、何も起きない操作になる。
- どの段階でどの操作ができるかが型と遷移関数に書かれるので、要る操作が抜けていれば（B-04）、テストで見つけやすい。
- 退ける案：サンプルのような旗の組み合わせ。ありえない組み合わせ（判定後で、かつ出題前、など）を表せてしまう。

### 3. 時間と副作用の扱い

| 選択肢 | 中身 |
|---|---|
| A | 遷移関数の中で、時計やタイマーを直接使う |
| **B** | **遷移関数は「何ミリ秒後に、この出来事を起こす」「その予約を取り消す」を副作用のデータで返し、実行器が `Scheduler` ポートで実行する。出来事には、実行器が `Clock` ポートの時刻を付けて渡す** |

**決定：B。** あわせて、前の問の何かが次の問に残らないように、次の3つを決める。

- 予約には、どの問のためのものかを付ける。今の問のものでない出来事が届いたら、遷移関数は無視する。
- 次の問へ進むとき、終わるとき、やり直すときは、前の予約を取り消す。
- 画面を離れるときは、実行器が予約をすべて取り消す。

**根拠**：B-16 の原因（前の問のタイマーが、次の問の札を判定した）が、構造の上で起きない。取り消しを忘れても、無視する仕組みが二重に守る。時刻は出来事に付いて届くので、遷移関数は純粋なままで、テストでは時刻を決めて渡せる。

共通の実行器が扱う副作用は、時間（予約と取り消し）だけにする。盤面の保存や画面の移動のような、モードごとの出口は、モードが結果のデータとして返し、そのモードの画面が扱う。

### 4. 共通にする範囲

| 選択肢 | 中身 |
|---|---|
| A | 1つの汎用の進行の仕組みを作り、各モードは、出題・判定・表示などを差し込み口に差し込む |
| **B** | **共通の契約（始める、操作を受ける、表示を作る）だけを決める。よく使う部品（進捗、結果の記録、次へ進む決まり）は部品として用意し、各モードが必要なものを組み合わせる** |
| C | 共通にしない。モードごとに一から書く |

**トレードオフ**：使い回せる量、に対して、違う流れを1つの形に押し込む無理。

**決定：B。**

- 4つのモードは、流れの違いが大きい。配置暗記の「覚える時間」と盤面の操作、実践練習の1文字ずつの表示と取るタイミング、複数枚の札を伏せる時間と1行の入力。A ではこれらのために差し込み口が増え続け、共通部分がモードの事情を知ることになる。
- C では、進捗・結果の記録・次へ進む決まりを、モードごとに書くことになる。サンプルで、モードごとに食い違った所（B-04、B-08、B-21）。
- B なら、新しいモードは契約を満たす部品として足せば済み、既存のモードと共通部分は変わらない（開放閉鎖）。部品は関数なので、使わないモードは使わなくてよい。

**共通の契約**（形の要点。細部は実装で決める）：

| 部分 | 中身 |
|---|---|
| 始める | 設定（そのモードに要る分）と、出題（乱数で作ったもの）を受け取り、最初の状態と副作用を返す |
| 操作を受ける | 状態と、コマンドまたは予約した出来事を受け取り、新しい状態と副作用を返す |
| 表示を作る | 状態から、画面に出すもの（表示用のデータ）を作る |

### 5. 結果の持ち方

| 選択肢 | 中身 |
|---|---|
| A | 全モードで1つの結果の型を使い、モードごとの違いは省略できる項目で持つ |
| **B** | **共通の部分は「正解・誤答・スキップ」の3つの結果だけ。そのほか（決まり字変化の有無、タイミングのずれ、理由など）は、モードごとの型で持つ** |

**決定：B。** 結果は、その回の状態の中に持つ。回が終わった後に保存はしない（今の仕様に、結果を残す求めはない。サンプルにも、結果を残す仕組みはない）。

- A は、使わない項目だらけの型になり、どのモードでどの項目が意味を持つかが型から読めない。
- 「スキップ」を共通の結果にするので、全モードで同じ扱いになる（取扱説明書 §8.1、B-19）。

### 6. 乱数・設定・時刻の渡し方

**決定**：

- 出題は、モードを始める前に、ユースケースが `Random` ポートと `domain` の関数（仕様 03）で作り、モードに渡す。遷移関数は乱数を使わない。
- やり直し（リセット）は、出題を作り直して、始めからもう一度始める。前の回の状態は何も引き継がない。
- 設定は、始めるときに、そのモードに要る分だけを受け取る（ADR-0003）。
- 時刻は、出来事に付いて届く（論点 3）。

**根拠**：遷移関数が乱数も時計も使わないので、テストで決めた値を渡すだけで済む。やり直しで状態を引き継がないので、B-13（リセット後に裏のまま残る札）の種類の不具合が起きない。

### 7. 表示の作り方

**決定：各モードが、状態から表示用のデータを作る関数を持つ。`ui` は、そのデータを表示し、操作をコマンドとして渡すだけにする。**

- 決まり字一覧の「未読・変化中」のように、表示にルールの計算が要るものも、`ui` の外で計算する（設計方針「`ui` はルールの計算をしない」）。
- 画面は、今の状態から作った表示だけを出すので、前の問の札が残る（B-07）ことがない。

### 8. モードどうしの受け渡し

**決定：配置暗記から実践練習へは、盤面を保存データ（`BoardRepository`）で渡す。モードどうしは、互いを直接呼ばない。**

- 実践練習は、保存された盤面がなければ、そのことを伝えて配置暗記へ移る案内を出す（取扱説明書 §5.4、確認済み）。
- 実践練習から戻ったときの盤面の扱い（§4.8）は、配置暗記の仕様で決める。

### 9. 置き場所

| 置く所 | 中身 |
|---|---|
| `application` の共通部分 | 契約の型、副作用の型、結果（正解・誤答・スキップ）の型、実行器（`Clock` と `Scheduler` で副作用を実行する）、よく使う部品 |
| `application` のモードごとの部分 | 各モードの状態・コマンド・遷移関数・表示を作る関数 |
| `ui` | モードごとの画面。実行器から表示用のデータを受け取って表示し、操作をコマンドとして渡す |
| `apps` | どのモードがあるかを組み立てる（合成ルート）。モードを足すときは、ここに1つ足す |

## この ADR で防ぐ不具合

| 不具合 | 防ぎ方 |
|---|---|
| B-24、B-04、B-08 | 段階を型で表し、各コマンドを意味のある段階でだけ扱う（論点 2） |
| B-16 | 予約に問を付け、前の問の出来事を無視し、進むときに取り消す（論点 3） |
| B-07 | 画面は今の状態の表示だけを出す（論点 7） |
| B-13 | やり直しは始めからもう一度始め、前の状態を引き継がない（論点 6） |
| B-19 | スキップを共通の結果にする（論点 5） |

## テスト

- 各モードの遷移関数：偽の時計と偽の予約で、時間が絡む流れも確かめる。
- 性質：どの段階でも、意味のないコマンドは状態を変えない。今の問のものでない予約の出来事は、状態を変えない。
- 実行器：予約と取り消し、画面を離れたときの全取り消し。
- 各モードの受け入れテスト（E2E）は、段階 4 の各モードの仕様から書く。

## この ADR で決めないこと

| 事項 | 決める所 |
|---|---|
| 各モードの段階・コマンド・結果の細部 | 各モードの仕様（段階 4） |
| 決まり字一覧などの見せ方、文言 | 各モードの仕様、文言の管理の ADR、画面に表示する情報の ADR |
| 入力デバイスからコマンドへの割り当て | 入力のアダプタ（設計方針 §2.4）。必要になったときに |
| 結果の保存、履歴、集計 | 今の仕様にない。必要なら提案として別に扱う |

## 却下した選択肢

| 選択肢 | 退けた理由 |
|---|---|
| 状態と処理を持つオブジェクトで、タイマーも中で使う | 前の問の処理が残りやすく、時間を待たないテストができない。サンプルの不具合が生まれた形 |
| 状態遷移のライブラリ（XState など） | 実行時の依存が増え、4つのモードの規模に見合わない |
| 旗の組み合わせで状態を表す | ありえない組み合わせを表せてしまう |
| 遷移関数の中で時計やタイマーを使う | テストで時間を決められない。前の問の予約が残る |
| 1つの汎用の進行の仕組みに、各モードを差し込む | モードの流れの違いが大きく、差し込み口が増え続ける |
| モードごとに一から書く | 進捗・結果・次へ進む決まりが、モードごとに食い違う |
| 全モードで1つの結果の型 | 使わない項目だらけになり、型から意味が読めない |

## 範囲と制約

### 標準でできること

- 時間が絡む流れを、実際の時間を待たずに、毎回同じ結果でテストできる。
- モードを、既存のモードと共通部分を変えずに足せる。
- 入力デバイスを足しても（ゲームパッドなど）、進行のコードは変わらない。

### 追加実装でできること（実施するかは別途判断）

- 結果の保存・履歴・集計。
- 状態の遷移を図にして確かめる道具。

### 諦めること

- 回の途中で画面を離れたとき、その回の続きから再開すること（状態を保存しないため）。サンプルにもない。

## この決定を見直す条件

- モードが増え、どのモードにも同じ流れが多く現れるようになったとき（汎用の進行の仕組みを考える）。
- 1つのモードの中で、同時に進む時間の流れが多く複雑になったとき（状態遷移のライブラリを考える）。
- 結果の保存や、回の途中からの再開が求められたとき。
