# ADR-0002: 乱数

- ステータス: 承認待ち
- 日付: 2026-10-31
- 改訂: 2026-11-01。種を指定できる擬似乱数を自作する案をやめ、`Math.random` を使う形に直した。設計方針の「シード指定可能」を外した。

## 背景

乱数を使うのは、出題の順番（シャッフル）、配る札・出す札の選び方、札の向き（[仕様 03](../spec/03-questions-and-dealing.md)）。設計方針は、`domain` が乱数を直接使わないこと、時刻と乱数をポートで受け取ることを決めている（[設計方針](../design/principles.md) §2.1〜§2.3）。

現行サンプルの使い方（コードで確認）：

- 乱数を使う所は7か所。出題順・配る札・配置暗記の出題順の5か所はシャッフル、札の向きの2か所は `Math.random() < 0.5`。
- シャッフルは5か所とも Fisher–Yates 法で、手順に偏りはない。`sort` に乱数を渡す、偏りのある書き方は使っていない。
- どこも `Math.random` を直接呼ぶので、テストで結果を決められない。

判断の仕方：誰が、何のために、同じ結果を必要としているかを先にはっきりさせ、その要件をどこで満たすのがいちばん安いかを決める。評価軸は設計方針 §1 の品質特性の優先順位。軸で差がつかなければ、費用と、後で変えるときの費用で決める。

## 決定

### 1. `domain` に渡す形

**0 以上 n 未満の整数を1つ返す関数を、引数で受け取る。**

- `domain` が要るのは「n 個から1つ選ぶ」ことだけ。シャッフルは「残り k 枚から1枚」、札の向きは「2つから1つ」。必要なものだけを受け取る（インターフェース分離）。
- テストで「何番目を選ぶか」を直接与えられる。取りうる組み合わせを全部与えれば、手順に偏りがないことを、統計ではなく全数で確かめられる。最優先の「ルールの正しさ」を、いちばん強い形で確かめられる。
- 小数を整数に直す処理は、アダプタの1か所に置ける。

### 2. 乱数の中身

**`Math.random` を使う。** `application` の `Random` ポートの実装（`packages/adapters-web`）で、`Math.floor(Math.random() * n)` によって 0 以上 n 未満の整数にする。

種を指定できる擬似乱数と比べると、評価軸で差がない。

| 評価軸 | `Math.random` | 種を指定できる擬似乱数 |
|---|---|---|
| ルールの正しさ | 手順の偏りのなさは、§1 の全数テストで確かめる。乱数の中身とは関係しない | 同じ |
| テスト容易性 | テストでは決めた値を与える（§5）。アプリの種は使わない | 同じ（種の出番がない） |
| 変更容易性 | ポートの裏にあるので、中身はアダプタ1つで替えられる | 同じ |
| 移植性 | どの公開先（ブラウザ、アプリの中の表示部品）にもある | 同じ |
| 性能 | 差がない | 差がない |

差は、今は要らない機能（ある回の順番の再現）のための費用だけ。自作なら、数十行の実装、参照実装との一致テスト、偏りのない整数化とその境目のテストが増え、保守し続けることになる。この決定は、ポートがあるので後から安く変えられる。必要になった日に、アダプタを1つ差し替えれば済む。

### 3. 設計方針の「シード指定可能」

**外す。** 方針は「乱数は `Random` ポートで受け取り、テストでは決めた値を返す偽の乱数を与えられること」にする。

- この方針の目的は、テスト容易性（すべての振る舞いを、毎回同じ結果で自動テストできること）。種はそのための手段の1つにすぎない。
- ポートの境目で決めた値を与えれば、目的は満たせる。手段を方針に書くと、要らない仕組みを強制する（この ADR の最初の案は、この書き方に合わせて自作を選んでいた）。

### 4. 偏りのなさの保証

**`Math.random` は、仕様どおりに動くと信じて使い、検証しない。確かめるのは、こちらの使い方（整数への直し方と、シャッフルの手順）。**

- `Math.random` の仕様（ECMAScript）：0 以上 1 未満の数を返す。その範囲でほぼ一様。作り方は環境しだいで、種は指定できない。
- 整数への直し方：`Math.floor(Math.random() * n)`。切り捨て（`floor`）を使う。切り上げ（`ceil`）では 1〜n になり、範囲がずれる。小数の細かさから来るわずかな偏り（100通りから選んで1億分の2以下）は、仕様の「ほぼ一様」の範囲として受け入れる。
- シャッフル：Fisher–Yates 法。後ろから順に、まだ決まっていない札の中から1枚を選んで入れ替える。k 枚を選ぶときは、シャッフルした先頭の k 枚を取る。どの k 枚の組も、同じ確からしさで選ばれる。

`Math.random` が正しくても、使い方を誤ると偏る。テストで見つけたい誤りの例：

| 誤り | 起きること |
|---|---|
| 整数化に `ceil` を使う | 0 がほぼ出ず、n が出る |
| シャッフルで `floor(Math.random() * i)` と書く（正しくは `i + 1`） | 札が元の位置に残る並びが一度も出ない。3枚なら6通りのうち2通りしか出ない |
| 毎回、全体の中から入れ替える相手を選ぶ | 並びによって出やすさが違う。3枚では 27 通りの結果を6通りの並びに分けるので、均等にならない |
| `sort(() => Math.random() - 0.5)` で並べ替える | 並べ替えの仕組みしだいで偏る |

### 5. テストでの乱数

| テスト | 方法 |
|---|---|
| `domain` の単体テスト | 選ぶ整数の並びを与える。シャッフルは、5枚までの札で取りうる組み合わせをすべて与え（5枚なら 5×4×3×2 = 120 通り）、どの並びもちょうど1回ずつ出ることを確かめる |
| `application` の単体テスト | 決めた値を返す偽の乱数を与える |
| 乱数のアダプタ | `Math.random` を差し替え、0 と 1 の直前の値でそれぞれ 0 と n−1 になることを確かめる。いろいろな n で、0 以上 n 未満の整数を返すことを確かめる |
| E2E（動きの確認） | 画面に出た札を読んで答える。札がどの歌かを、画面から読めるようにする（札の画像の名前など。読み上げのためにも要る。詳しくは各画面の仕様） |
| E2E（見た目の比較） | テストの側で、ページが読み込まれる前に `Math.random` を決めた値を返すものに差し替え、毎回同じ盤面にする。テストのための仕組みは、アプリに入れない |

### 6. 札の向き

仕様 03 §4・§5 のとおり、札流しは1枚ごと、複数枚は問ごとに、ほかと関係なく半々で決める（サンプルと同じ）。次の向きを予想できないことを優先し、少ない枚数で片方の向きに偏ることは受け入れる（例：3枚がすべて同じ向きになる確からしさは 25%）。ユーザーの決定（2026-10-31）。

## 却下した選択肢

| 選択肢 | 退けた理由 |
|---|---|
| `domain` が `Math.random` を直接呼ぶ | 設計方針に反する。テストのたびに結果が変わり、ルールの正しさを毎回同じ結果で確かめられない |
| `domain` が 0 以上 1 未満の小数を受け取る | 整数に直す処理と偏りの扱いが、`domain` のあちこちに散らばる。テストで狙った選択を作りにくい |
| 乱数の状態を値で渡し、新しい状態を返してもらう | `domain` は完全な純粋関数になるが、テストでの得は整数を返す関数と同じ。呼ぶたびに状態を受け渡す手間だけが増える |
| 種を指定できる擬似乱数を自作する（xoshiro128\*\* など） | 評価軸で差がなく、今は要らない機能のための実装・テスト・保守が増える。この ADR の最初の案だったが、2026-11-01 に退けた |
| 乱数のライブラリ（pure-rand など） | 上と同じ理由に加え、実行時の依存が増える |
| `crypto.getRandomValues` で、正確に一様な整数を作る | 予想できないこと（暗号の強さ）は要らない。`Math.random` との正確さの差は観測できず、コードが増える |
| 札の向きを、ちょうど半分ずつにする、または同じ向きが続く回数に上限を付ける | 偏りは減るが、終盤や上限に来たときに次の向きが分かる。ユーザーの決定で、予想できないことを優先した |

## 範囲と制約

### 標準でできること

- テストでは、決めた値を与えて、毎回同じ結果にできる（単体テストも E2E も）。
- `domain` のシャッフルは、取りうる組み合わせを全部与えて、偏りがないことを全数で確かめられる。

### 追加実装でできること（実施するかは別途判断）

- 練習の回を、同じ順番で再現する（報告された回の再現など）。種を指定できる乱数のアダプタに差し替える。新しい機能なので、提案として別に扱う。

### 諦めること

- 本番のアプリで、ある回の順番を後から再現すること。
- 環境（ブラウザ）が違っても、同じ並びになること。

## この決定を見直す条件

- 回の再現を、機能として入れるとき。
- 複数の機器で、同じ順番が要るようになったとき（例：2人で対戦する機能で、両方の端末に同じ読み順を出す）。
- 重み付きの確率など、整数の選び方では表せない乱数が要るようになったとき（渡す形を足す）。
